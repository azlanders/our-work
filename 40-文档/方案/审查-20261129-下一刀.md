# 审查：616/714 下的下一刀

日期：2026-11-29  
范围：只读审查 `dsh/vendor/dsh-mnemonic` 与本地 CMB A/B 脚本，不改生产代码，不跑全量。  
口径：任务书的 616/714 是当前基线；本文的收益估计都是方向性预估，没有跑 714 全量，也没有把旧批次的 594/624 当成当前基线。

## 0. 结论

**第一刀不是改 `profile.js`、`openloops.js` 或 `recall.search()`，而是改 CMB inline 臂的证据契约尾注。**

原因是评分链路不对等：

- `bench-fixed-ab.mjs:152-176` 只调用 `renderRecallBlock()`，再拼 `SYSTEM`、记忆块和用户问题；它不经过 `index.js` 的自动回忆、`profileSlots()`、`openLoops()` 或 `recall.search()`。
- `card.js:256-263` 的 `RECALL_RULES` 也不在这条链路里；`bench` 自己在 `47-55` 行拼 `SYSTEM_BASE`。
- 因此，`profile` 的“现在住在哪”修复、`openLoops` 的长约定修复、`recall` 的时间路由，对 616 的直接贡献都接近 0；它们会改善真实聊天，但不能解释这次分数。

当前 inline 臂用的是 29 字的 `TAIL_BASE`（`45` 行），只说了“别念原文、没有就记不清”。它没有覆盖任务书点名的四类问题：旧状态压新状态、计划当已发生、相对日期换算、纠错/矛盾取舍。`TAIL_TRAIL`（`44` 行）已经有“最晚那条、计划不是已发生、只答问到的点”，但默认 inline 没用它；而且它仍缺“后文明确更正前文就按更正答”这一句。

所以第一刀建议是：**新增一个约 96 字的 `TAIL_CONTRACT`，只给 inline 臂替换尾注，做 150 题配对 A/B。** 具体文本和补丁见 §5。

## 1. 616 实际经过的链路

`bench-fixed-ab.mjs` 的答案生成路径是：

1. `selectHits()`（`81-107`）从预计算的 `block.pool` 取命中，`diversify()` 选最多 5/8 条，再 `groupAdjacent()` 补邻轮。
2. `renderFixed()`（`152-168`）按 `isMultiNeedQuery()` 决定 1200/1800 字、200/260 字每条的预算。
3. `renderInline()`（`109-125`）调用 `renderRecallBlock()`（`card.js:278`）。
4. `messagesFor()`（`170-176`）拼成：`SYSTEM` + `【现在】`、`【记忆摘录】` + block、用户问题。
5. `chat()`（`186-208`）调用模型；`stripRefs()`（`178-184`）剥掉 `[M#]` 后落盘。

这条链路没有 `index.js:821` 的 `agent/pre-step`，也没有 `index.js:1007` 的 `openLoops()`、`998-1002` 的 `profileSlots()`、`963` 的 `recall()`。`RECALL_RULES` 也不在 `messagesFor()` 里。

**结论：任何只改 `index.js` 自动回忆或生产 system prompt 的补丁，在 616 上测不到。** 研究文档里“CMB 跑分不走 `RECALL_RULES`”这一点，在当前脚本里仍然成立，而且更窄：连 `asstOnly`、`terms`、`profile`、`openLoops` 都没传。

这个结论以“616 由这份 `bench-fixed-ab.mjs` 产生”为前提；任务书把它列为本地 A/B 入口。如果服务器全量用的是另一份脚本，先核对入口，再把本文的“评分链”结论套过去。

## 2. 逐文件证据

### 2.1 `lib/card.js`

**与 616 直接相关的部分**

- `256-263`：7 条 `RECALL_RULES`。它要求“引用旧事只用 `[M#]`”“没写就说记不清”“计划别当已做”，但 `bench` 不使用它；在 CMB 上改这段是零收益。
- `269`：`RECALL_TAIL` 是 51 字短尾注，强调“别念原文、没有就记不清”，没有“最晚一条优先”“计划不是已发生”“更正优先”。
- `278`：`renderRecallBlock()` 是 CMB 唯一实际使用的渲染入口。
- `286-304`：按 `canonicalId || id` 折叠近似重复；同一 canonical 组里只在“前一条已作废、当前条未作废”时换人，否则先到先得。若命中顺序把旧值排在前面，当前值可能被折叠掉。
- `306-331`：块头、`replacedIds`、`nowLine`。这里有一个可复现的空行 bug：当旧值在块里、后继在当前 `byId` 里但不在 `hits` 列表里时，`replacedIds` 会加入后继 id，`nowLine` 却只在 `list` 里找它，最后渲染出空的 `（现在：）`。
- `358`：行首是 `[M1]`，不是 `1.`。这直接解释了 §2.7 的 `usedTurns` 计数 bug。
- `362`：正文相对日期的锚点是 `spokenAt ?? eventAt ?? createdAt`。
- `366-368`：`eventAt` 与锚点相差超过一天时，标 `〔计划〕` 或 `〔事发〕`。这是“计划不是已发生”的结构信号，但 CMB 的 `recordsFor()` 不生成 `supersededBy`，也不保证 `eventAt` 与 `spokenAt` 分离，所以很多计划/变更题拿不到这个标记。
- `371`：只有第一条可以享受 `firstItemChars` 加宽；默认 `firstItemBoost=1`（`index.js:239`），实际不加宽。
- `387`：`renderBody()` 接收 `terms`，用于 `focusWindow()` 选中间窗口；`terms` 缺失时退回“头 55% + 尾 45%”，长证据的中间句会被切掉。
- `390-408`：预算装不下时，后续条目只有剩余正文 ≥40 字才裁短；否则整条丢弃。
- `413-422`：顺序是 head / hint / body / notice / nowLine / profile / tail。`nowLine` 在正文之后、画像之前；对“现在是什么”的问题，它是一个位置锚。

**判断**

`card.js` 的结构已经有多数需要的信号（`[M#]`、日期、计划、旧说法、当前说法），但 CMB 的数据没有 `supersededBy`，所以 `377-385` 的旧/新标记和 `324-331` 的 `nowLine` 大多不触发。CMB 上真正能补的是尾注契约，而不是再加一条 `RECALL_RULES`。

### 2.2 `lib/recall.js`

- `82-109`：`groupAdjacent()` 默认只补 30 分钟内的下一条；CMB 显式传 48 小时（`bench:106`），所以会补进更多“同话题但不是答案”的邻轮。
- `118-124`：`timeOf()` 只要查询含“聊/说/提/问/告诉/讲/对话/回复”，就按 `spokenAt`；否则按 `eventAt`。这对“上次说”是对的，但对“说好什么时候还”这类时间约定会把“说”当成说话时间，可能拿错时间轴。
- `151-152`：只有查询有二元组、扩词、别名或时间窗才继续。
- `177-226`：活跃文档 IDF、候选集、时间窗候选。时间窗最多补 64 条，按记录从新到旧扫描。
- `237-241`：`excludeIds`、`muted`、`scope` 的硬过滤。
- `298-305`：旧值分数可降到 `minScore * 0.8`，但解析出的当前值仍要按自己的分数过闸；当前值不过闸就整条丢掉。
- `314-323`：当前值的 `entryScore` 用 `hitRec` 重新算，避免旧值借当前值的分数混进来。

**判断**

`recall.js` 的时间窗和旧值解析本身没有看到 616 能直接吃到的明显断点；它不在 CMB 链路里。真正的问题在 `index.js:924` 的 `wantsRecall` 没覆盖“什么时候/哪天/几号/多久”，导致时间题可能走 soft 预算和 `proactive` 日配额；这是生产侧问题，不是这次 616 的第一刀。

相邻发现（`lib/text.js`，只读核对时用到）：`extractTimeWindow()` 在 `292-296` 行先判“前天/前日”，再判“大前天”，但“大前天”包含“前天”，所以纯函数探针得到 `大前天 -> { label: '前天' }`。这是确定的相对日期分支顺序错误；它影响生产检索时间窗，不影响 `bench` 的预计算 `pool`，因此同样不放进第一刀，但应进入第二波。

### 2.3 `lib/supersede.js`

- `8-24`：从 `supersededBy` 走到真正当前值；断链、成环、跨 scope、静音、超过 8 跳都返回 `null`。
- `16-17`：兼容两种字典值：命中对象 `{ rec }` 和记录本身。
- `19-21`：只拒绝“有 scope 且不是本会话”的后继；无 scope 的全局记录仍可见。

**判断**

逻辑本身没有发现需要为 616 改的点。它的收益依赖 `supersededBy` 元数据；CMB 的 `recordsFor()`（`bench:68-77`）没有写这个字段，所以 `resolveCurrent()` 在 CMB 上基本没有输入。

### 2.4 `lib/openloops.js`

- `97-111`：`dueOf()` 先找 `MANUAL_DATES`，再用 `resolveRelativeDates()`；有未来日期就优先未来，全部在过去才退回最早。
- `110`：它取“第一个不早于今天的日期”，不是“动作所对应的那个日期”。例如“明天去医院，后天告诉你结果”，会取明天而不是后天。
- `180-201`：`openLoops()` 的年龄过滤是 `now - at > maxAgeDays * DAY`，`at` 是 `spokenAt`（`189`），不是 `dueAt`。一句 20 天前说的“下个月给你答复”会在默认 14 天时被丢掉，即使约定还没到期。
- `229-260`：渲染最多 3 条，按 `dueAt` 升序，`maxLines/maxChars` 控制输出。

**判断**

这是真实聊天里的高价值问题，但 CMB `bench` 不调用 `openLoops()`；对 616 是零直接收益。适合第二波生产修复，不适合第一刀。

### 2.5 `lib/profile.js`

- `12-22`：宽松的 `SLOT_RULES`，用于渲染画像。
- `26`：`FLEETING_RE` 包含“现在/目前/今天/最近”等。
- `30-42`：严格的 `HARD_RULES`，用于决定能否作废旧值。
- `80-89`：`stableAttrOf()` 先跑 `HARD_RULES`；没命中再看 `FLEETING_RE`，命中就返回空。
- `95-129`：`profileSlots()` 优先 `stable`，`loose` 只补空缺；同槽位按 `eventAt || createdAt` 取较新。

**可复现问题**

`HARD_RULES` 的住处/工作/称呼都要求动词紧跟在“我/俺”后，例如 `我住在`、`我在…上班`。但 `FLEETING_RE` 又把“现在”当成临时词。结果：

```text
我住在徐汇              -> 住处
我现在住在徐汇          -> ""
我目前住在徐汇          -> ""
我在便利店上班          -> 工作
我现在在便利店上夜班    -> ""
我换工作了，现在在便利店上夜班 -> 工作
我叫小明                -> 称呼
我现在叫小明            -> ""
```

后果在 `index.js:619-655`：`slot = stableAttrOf(rec)` 为空，就不会把旧住处/旧工作作废；`profileSlots()` 的 `stable` 仍保留旧值。用户说“我现在住在徐汇”，画像和检索仍可能拿旧地址当现在。这是“旧状态压新状态”的典型，但它是生产链路问题，CMB 不经过 `profile`，所以不是这次的第一刀。

### 2.6 `index.js`

**与 616 无关但重要的主链路**

- `237-274`：默认预算 `injectChars=900`、`itemChars=200`、`limit=4`；`multiInjectChars=1800`、`multiLimit=8`；`softInjectChars=600`、`softLimit=3`。
- `382-406`：`recall()` 走 `search()`；`scope`、`allowSuperseded`、`allowRepeat` 在这里进入。
- `523-657`：`archiveTurn()` 存上一轮问答；`549` 用助手消息时间做 `msgTs`，`567` 同时写 `eventAt` 和 `spokenAt`。
- `619-655`：`stableAttrOf()` 命中且 scope 存在时，才作废旧槽位；`multi/planned/explicit/definitional` 决定 `mayReplace`。
- `807`：常驻卡只渲染 `store.records.filter((r) => !r.scope)`。但 `archiveTurn()` 在 `525` 行没有 scope 直接返回，`mem_save` 在 `695` 行没有 scope 也拒绝写入；当前正常写入都带 scope，所以这张“常驻状态卡”在现行数据上基本为空。这是一个结构性死路径，但 CMB 不读它。
- `892-900`：`CORRECTION_RE` 命中后只给上一轮注入的记录打 `disputedAt`，三天内降分到 0.6；不修改内容、不建立新值。真正的“更正”要等下一轮归档，且新句必须命中 `stableAttrOf` 才会作废旧值。
- `924`：`wantsRecall` 覆盖“记得/上次/上回/那天/生日/叫什么/住哪/多大/几岁/老家”，**没有“什么时候/哪天/几号/多久/多长时间/周几”**。
- `929-936`：`wantsRecall` 决定是否查询改写、是否用满档 1200/200；否则走 600/180 的 soft 档。
- `940-966`：`metaRecall` 按最近记录倒着数；普通检索走 `recall()` + `diversify()`。
- `971-973`：`proactive = !chitChat && !stopRecall && !wantsRecall && !metaRecall`。时间问句若没命中 `wantsRecall`，会被当成主动提起，受 `proactiveDailyLimit=2` 限制；当天两次之后 `hits=[]`。
- `1007-1018`：`openLoops()` 只取当前 scope，`dueAt` 过期两天以上不显示；这正是 §2.4 的 14 天年龄问题会叠加的地方。
- `1026-1036`：明确回溯但一条没翻到时，系统侧加“这次没翻到”提示；这能防止硬编，但也会放大“时间问句没走 wantsRecall”的问题。
- `1048-1064`：同槽位两种活说法时只加一句“同一件事有两种说法，按最近那条”；没有结构化冲突渲染。
- `1082-1090`：`asstOnly` 只在“用户半段覆盖率低、助手半段覆盖率高”时标记 `〔她说的〕`；这是 CMB 缺失的生产能力之一。
- `1092-1103`：生产渲染传了 `terms: focusTerms(...)`、`asstOnly`、`byId`、`scope`；`bench` 只传了 `maxChars/itemChars/firstItemChars/now/tail`。
- `1189-1209`：回忆块插在提问之前；这是已有实测的位置收益，不要在下一刀里动。

**判断**

`index.js` 里至少有三个真实问题：时间问句没进 `wantsRecall`、纠错只降分不建立新值、常驻卡按 `!scope` 过滤导致空卡。但前两个都发生在 `bench` 不经过的自动回忆链路；第三个连 CMB 都不读。它们应该排在 616 第一刀之后。

### 2.7 `bench-fixed-ab.mjs`

- `21-25`：默认 `PROMPT_VARIANT='base'`，默认 arms 是 `inline,trail`。
- `44`：`TAIL_TRAIL` 已有“最晚那条、计划不是已发生、只答问到的点、不补未问细节、括号日期直接用”，但它是 trail 臂的尾注。
- `45`：`TAIL_BASE` 只有 29 字，默认 inline 使用它。
- `46`：`TAIL_CITE` 已有“每句指得到 `[M#]`、指不到删、能答的先答、日期只抄”，但只有 `PROMPT_VARIANT=cite` 才启用。
- `47-55`：`SYSTEM_BASE`。第 `48` 行写“摘录里出现过的事就是真的发生过”，第 `51` 行写“只回答被问到的”，第 `52` 行只禁止没出现过的未来时间，第 `54` 行写“确实没有就说记不清”。它没有“现状按最晚那条”“计划不是已发生”“后文更正优先”。
- `56-60`：`PROMPT_VARIANT=cite` 只追加第 6 条并换 `TAIL_CITE`；默认 `base` 不追加。
- `62-79`：`recordsFor()` 生成的记录只有 `id/turn/text/createdAt/eventAt/spokenAt/scope/keywords`，没有 `supersededBy`、`canonicalId`、`asstOnly`。所以 `card.js` 的旧/新标记在 CMB 上没有输入。
- `81-107`：`selectHits()` 使用预计算 `block.pool`；`diversify()` 选 5/8 条，`groupAdjacent()` 用 48 小时补邻轮。
- `109-118`：`renderInline()` 调用 `renderRecallBlock()` 时**没有传 `terms`、`asstOnly`、`byId`、`hint`、`profile`**。生产在 `index.js:1092-1101` 传了这些。
- `119-120`：`rendered = block.match(/^\d+\. /gm)`。但 `renderRecallBlock()` 的行首是 `[M1]`（`card.js:358`），所以这个正则永远数到 0；`usedTurns` 永远是空数组。我用 3 道题跑了 `CMB_DRY=1`，输出均为 `usedTurns: []`。
- `127-150`：`renderTrail()` 的尾部固定用 `TAIL_TRAIL`，不是 `TAIL`；所以 `PROMPT_VARIANT=cite` 对 trail 臂无效。
- `152-168`：`renderFixed()` 的 `limit` 是 5/8，预算 1200/1800；它不按时间题、纠错题、矛盾题做任何路由。
- `170-176`：`SYSTEM + renderClock()`、`【记忆摘录】`、用户问题；没有 `RECALL_RULES`。
- `178-184`：`stripRefs()` 剥 `[M#]`，但不会修正答案里的日期或矛盾。
- `233-285`：`runLive()` 按 id 交替 arm，落盘答案和 `usedTurns`；`263` 行的缩进不齐，不影响运行。

**可复现的 fidelity 问题**

以 `P14-CASE-batch-suv/d00` 为例，`renderInline()` 没有 `terms`，`renderBody()` 走默认头 55% + 尾 45%，用户半段被切成：

```text
...前两天你问我是不是有辆白色S…走。说起来也怪，我这岁数还没车...
```

关键原句“那辆白色SUV是李楠的”落在中间被切掉；助手半段还保留了“白色SUV是李楠的”，所以这题不是完全没救，但归属和证据完整度已经降级。生产 `index.js` 传了 `terms`，`focusWindow()` 会优先保留含“SUV/李楠/地铁/打车”的窗口；bench 没有。

另一个例子是 `P01-ADD-004/d00`：block 里已经有 `上周五(2026-06-05)`，但 `TAIL_BASE` 不要求“问哪天就用括号里的换算”，模型仍可能自己算。`TAIL_TRAIL` 和 `TAIL_CITE` 都更明确。

## 3. 候选比较

权重按任务书：正确性 35%、迁移/回滚风险 20%、token/延迟 15%、可维护性 15%、扩展性 10%、安全 5%。这是排序权重，不是精确评分。

| 候选 | 做什么 | 616 直接收益 | 成本/风险 | 判断 |
|---|---|---:|---|---|
| A 保留现状 | 不改 | 0 | 0 | 不采纳；四类优先问题仍靠 29 字尾注 |
| B 局部改：inline 证据契约尾注 | 只替换 inline 臂尾注，约 96 字 | 方向性 +10~20 题（未实测） | +67 字；可能过度弃权/丢一条证据 | **推荐第一刀** |
| C 局部改：bench fidelity | 补 `terms`、`asstOnly`、修 `usedTurns` 正则 | 方向性 +5~12 题 | 只改测量脚本，不改生产；但会改变基线 | 作为 B 的前置测量修正，不单独当第一刀 |
| D 重构：query-aware evidence policy | 按时间/矛盾/纠错/多问点路由，统一改 `card`、`index`、`bench` | 方向性 +15~25 题 | 跨 3 个文件、需要新测试和回滚；当前证据不足 | 不在本轮做 |
| E 生产修复：profile/openLoops/supersede | 修“现在”槽位、长约定、空 `（现在：）` | 对 616 约 0 | 真实聊天收益高；但评分链不经过 | 第二波，不进本轮 A/B |

### 为什么不先做 E

`profile.js` 的“我现在住在徐汇”识别失败、`openloops.js` 的 20 天前长约定被 14 天过滤掉、`card.js:324-331` 的空 `（现在：）`，都是真问题，而且都能用纯函数复现：

```text
stableAttrOf("我现在住在徐汇") -> ""
openLoops(20 天前的“下个月给你答复”, maxAgeDays=14) -> []
旧值在块内、当前值只在 byId 时 -> "（现在：）"
```

但 `bench-fixed-ab.mjs` 没有调用它们，616 不会因为修它们而变化。先修它们会让“生产更好”，却无法回答“这刀在 616 上值多少”。所以放在第二波，等 616 的子集方向确定后再做。

### 为什么不先做 D

query-aware 路由是正确方向：时间题按事件时间升序、矛盾/纠错题按新旧排序、多问点题扩预算。它也能同时解决 `index.js:924` 的时间词缺失和 `bench:152-168` 的无路由。但它至少要改三个入口，且当前 150 题里没有“路由前后”的配对数据；先上会把“路由收益”和“尾注收益”混在一起，重演 `inline/trail` 这种多变量 A/B 的归因问题。

## 4. 推荐第一刀：inline 证据契约尾注

### 4.1 目标

只改 CMB inline 臂的尾注，不动卡片结构、不动检索、不动生产 `RECALL_RULES`、不动 `profile/openloops`。用一个变量隔离“尾注措辞”的净效果。

### 4.2 候选文本

```text
（问题里能答的先答，缺哪项说哪项；只答问到的点，不补未问细节。每句指得到 [M#]，指不到的删。现状和进度按最晚那条，计划不是已发生；后文明确更正就按更正答，否则矛盾都列。日期只抄括号里的。）
```

长度 96 字；比现有 `TAIL_BASE` 多 67 字。它把任务书点名的六类问题压成四个动作：

1. 能答的先答、缺项单说：防止过度弃权，也防止漏多问点。
2. 只答问到的、不补未问细节：对应“未知当事实”和 `corr-diag` 里的“多补一句入职日期/刻度时间”。
3. 现状/进度按最晚、计划不是已发生：对应真实变化、时间约定、计划题。
4. 后文明确更正优先，否则矛盾都列：对应纠错和没解释的矛盾。
5. 日期只抄括号：对应相对日期/时间题。

最后一条“日期只抄括号里的”依赖 block 里已有 `inlineDateHints()` 的换算；`card.js:149/161` 已经在正文里插了 `(YYYY-MM-DD)`。如果没有这个括号，模型仍可能自己算，这是本刀的已知边界。

### 4.4 同轮必须做的两个测量修正

这两个不改变答案，只让指标可信；不要把它们的收益算进第一刀：

- 在 `CMB_DRY=1` 下检查所有 150 题的 `overBudget`；`TAIL_CONTRACT` 比 base 多 67 字，可能让最后一条证据被挤掉。若 `overBudget=true` 或 block 少一条关键行，先把尾注压到 80 字，不要加预算。

`terms/asstOnly` 的补齐是更强的 fidelity 修正，但它是第二个变量：先记录当前 inline 基线，再单独开 `inline+terms/asstOnly` 臂，不要和尾注同轮混在一起。

## 5. 风险与回滚

### 风险

1. **过度弃权**：`指不到的删` 可能让模型把“能答但没显式引用”的细节也删掉，尤其多问点题。监控 `required` 里本可答的项从有到无。
2. **约束过载**：96 字里塞了 5 个动作，弱模型可能只执行前两条。若 `time`/`contradiction` 切片不涨，说明后半段没被执行。
3. **证据被尾注挤掉**：+67 字约等于 1/3 条 200 字证据；长 block 可能少一条。用 dry run 的 block 行数和关键行覆盖检查。
4. **归因错误**：如果同轮还改 `terms/asstOnly`，无法知道收益来自尾注还是渲染。第一轮只允许尾注一个变量。
5. **生产迁移风险**：CMB 的 `SYSTEM` 不是生产 `RECALL_RULES`。即使 150 题通过，也不能直接把这段文本塞进 `card.js:256` 就上线；生产要单独改 `RECALL_RULES`/`TAIL` 并再跑生产侧检查。

### 回滚点

- A/B 阶段：删除 `contract` 分支或把 `CMB_ARMS` 改回 `inline`，旧答案 JSONL 不动；零数据迁移。
- 生产阶段（如果后续批准）：只回滚一个常量/一个 `tail` 参数，不改 `store` schema、不作废记录、不迁移 JSONL；旧块可随时用 `TAIL_BASE` 重渲染。
- 全量门槛：150 题净增 <0，或“错否”增加 >5 题，立即回滚；净增 8~14 只允许扩大样本，不允许直接推生产。

## 6. 150 题子集验证判据

### 6.1 样本与配对

- 样本：`C:\Users\28245\Documents\deepseek-harness\default-workspace\.tmp\cmb-local\rows-weak150.json`，150 个 id。
- 命中：固定 `blocks-w-hint.jsonl` 的 `pool/turns`，两臂完全同一组命中；不改检索。

### 6.2 主指标

- 整题通过数：`gain - lose`。
- **接受阈值：净增 ≥ +15**（任务书门槛），且 `lose ≤ gain / 2`。
- 方向性继续：净增 +8~14，扩大到 300 题复测，不直接上生产。
- 回滚：净增 <0，或净增 >0 但“错否”增加 >5 题。

### 6.3 分桶判据

150 题里按问题文本做的粗筛上限（不是 gold 标签）：时间类约 40 题、变化/现状类约 53 题、纠错/矛盾类约 16 题、约定/计划类约 18 题、相对日期类约 12 题。用同一批 id 做切片，至少满足两条：

- 纠错/矛盾切片净增 ≥ +4；
- 真实变化/现状切片净增 ≥ +5；
- 时间/相对日期切片净增 ≥ +4，且日期误删 ≤3；
- 任一 judged tag 不得净降 >2 题。

如果只有“资料不足”涨、其他切片不动，说明尾注只是让模型更谨慎，不是真的解决了矛盾/变化；不采纳。

### 6.4 副作用

- **错否**：证据里有必需事实，答案却说“没提过/记不清”的题数，增加 ≤3。
- **答案长度**：中位数增幅 ≤20%，`max_tokens` 截断率不上升超过 5 个百分点。
- **日期**：多写/写错日期的题数 ≤3；相对日期括号被删 ≤3。
- **覆盖**：`usedTurns` 非空率、`renderedIds` 数量不得下降；如果尾注挤掉一条证据，记录具体 id，不要用“总分涨了”掩盖。

- 不跑 714 全量；150 题通过前不进入生产候选。
- 不跑 free-form self-review；研究文档已说明三次自纠是负期望。
