# 调研-20261128-第五轮-开源代码-纯聊天压缩

范围：主流 AI 编程/聊天 agent 如何压缩**纯聊天历史**，只抄机制，不抄文案。

结论先行：

- 真正做“聊天历史压缩”的主流实现只有三条路线：**头尾切分后摘要中段**（aider、OpenHands、Letta）、**按 token 保留近期尾部后摘要前段**（Cline 新一代）、**不摘要，只做事实抽取/检索**（mem0、Zep）。
- 所有能长期跑的方案都不是“每次把全史重新总结一遍”，而是**滚动摘要 + 只折叠新增消息**。差别在于切点怎么选、头部保护什么、摘要写成什么结构。
- 头部保护最常见的是 system prompt；aider 和 OpenHands 还额外保护最早的用户消息。这个做法在长任务里出过事故：后来的新任务会被第一条旧任务压住（OpenHands #19337）。
- 摘要 prompt 的硬约束比文风重要：必须保留文件名/函数名/ID/URL/用户原话；必须禁止续写、禁止调用工具；必须限制字数；必须允许“上一版摘要”作为输入。
- 对 QQ 纯聊天 bot，最值得抄的是 **Cline 的“只折叠上一版摘要之后的新消息”** 和 **Letta 的“摘要字段化 + 保留原话 + lookup hints”**，而不是 aider 的 1/16 小预算或 OpenHands 的事件墓碑。

证据分级：

- **源码级**：直接读到关键函数本体。
- **文档级**：只有官方文档/博客，没有读到实现。
- **二手代码审读**：第三方对某个 commit 的逐行分析，降权使用。

## 1. aider

仓库：`Aider-AI/aider`（用户写的 `paul-gauthier/Aider` 是旧地址）

关键文件：

- `aider/history.py` → `ChatSummary.summarize()` / `summarize_real()` / `summarize_all()` / `too_big()`
- `aider/coders/base_coder.py` → `summarize_start()` / `summarize_worker()` / `summarize_end()` / `move_back_cur_messages()` / `format_chat_chunks()`
- `aider/models.py` → `Model.max_chat_history_tokens`
- `aider/prompts.py` → `summarize` / `summary_prefix`

### 触发条件

`base_coder.py` 的 `summarize_start()`：

```python
if not self.summarizer.too_big(self.done_messages):
    return
```

`too_big()` 就是把 `done_messages` 逐条 token 化后求和，超过 `max_tokens` 就触发。它**不看当前轮**，只看已经归档的 `done_messages`。

`max_tokens` 不是固定 1024。`BaseCoder.__init__` 传入 `self.main_model.max_chat_history_tokens`，而 `models.py` 里算是：

```python
self.max_chat_history_tokens = min(max(max_input_tokens / 16, 1024), 8192)
```

也就是模型输入窗口的 1/16，夹在 1k–8k 之间。对 128k 模型是 8k；对 32k 模型是 2k。

触发时机在 `move_back_cur_messages()`：当前轮结束后，把 `cur_messages` 并入 `done_messages`，然后启动后台线程摘要；`format_chat_chunks()` 里 `summarize_end()` 再 join，避免阻塞模型调用本身，但会阻塞下一轮 prompt 组装。

### 切分与保留规则

`summarize_real()` 的逻辑：

1. 总 token 未超预算且 `depth == 0`，原样返回。
2. `min_split = 4`；消息太少或递归深度 `> 3`，直接整段 `summarize_all()`。
3. 从尾部反向累加，尾部预算固定为 `max_tokens // 2`，得到 `split_index`。
4. 从 `split_index` 往前退，直到头部最后一条是 `assistant`，保证头尾角色边界干净。
5. 如果 `split_index <= 4`，整段摘要，不切。
6. 头部再按 `model_max_input_tokens - 512` 截一次。**注意：它是从最老的消息往后装，装满为止**，不是保留靠近尾部的头部。
7. `summary = summarize_all(keep)`；如果 `summary + tail` 仍超预算，就把“摘要+尾部”当成新列表，`depth + 1` 再递归。

`summarize_all()` 只保留 `USER` / `ASSISTANT`，格式化成 `# USER\n...` / `# ASSISTANT\n...`，然后：

```python
summarize_messages = [
    dict(role="system", content=prompts.summarize),
    dict(role="user", content=content),
]
```

摘要返回后加上 `summary_prefix`，包成一条 `user` 消息：

```python
summary = prompts.summary_prefix + summary
return [dict(role="user", content=summary)]
```

`summary_prefix` 是：

```text
I spoke to you previously about a number of things.
```

如果最后一条不是 assistant，会补一条 `assistant: "Ok."`，保证下一轮角色交替合法。

### 摘要 prompt 的关键约束

`aider/prompts.py` 的 `summarize`：

- `*Briefly* summarize`：明确要短。
- 越老的部分越略，越新的部分越详。
- 话题变化就换段。
- 禁止用 `Finally, ...` 收尾，因为摘要只是一段中间历史，后面还会继续。
- **必须**保留正在讨论的函数名、库名、包名。
- **必须**保留 assistant 在 ```...``` 代码块里引用过的文件名。
- **禁止**摘要里出现 ```...``` 代码块。
- 用用户第一人称写，把 assistant 称作 `you`，开头必须是 `I asked you...`。

这套 prompt 的目标不是“客观会议纪要”，而是“让模型以为这是用户自己说的一段回忆”。对聊天 bot 来说，这个视角值得借鉴，但“禁止代码块”不适用于聊天。

### 已知 issue / 踩坑

- [#5440 Chat summarization retains the oldest head messages](https://github.com/Aider-AI/aider/issues/5440)：头部超预算时从最老的消息开始保留，导致“紧挨着尾部、最近的前文”被丢掉，反而留下很早的内容。这是第 6 步的直接后果。
- [#5878 `/code` without arguments summarizes and replaces the chat history](https://github.com/Aider-AI/aider/issues/5878)：模式切换路径误触发摘要，历史被替换。
- [#2979 Restoring chat history leads to error / summarization not working](https://github.com/Aider-AI/aider/issues/2979)：摘要模型/provider 失败时，恢复历史直接报错。

### 可借用点

- `max_input_tokens / 16` 的预算思路：摘要不该和主上下文抢空间，给一个明确的小比例上限。
- 尾部固定 `max_tokens // 2`，头部摘要，结构简单、可预测。
- 切点必须落在 assistant 边界，避免角色交替错位。
- 递归深度上限，防止“摘要的摘要的摘要”无限套娃。
- prompt 里明确“保留标识符、不要收尾、不要代码块”，比泛泛写“总结一下”有效。

### 不采用的原因

- 1k–8k 的预算对 QQ 长期人格聊天太小，会频繁摘要、丢细节。
- 头部“从最老开始装”是已知 bug，不能照抄。
- 摘要直接替换 `done_messages`，原始历史在上下文里不可回看；QQ bot 需要保留原始日志供检索和纠错。
- 没有“固定人格/关系状态”保护层。

### 可量化判据

- 200 轮合成聊天、植入 40 条事实，压缩后事实召回 ≥ 90%。
- 摘要 token ≤ 被压缩段 token 的 15%，且 ≤ 1200 token。
- 最近 8 轮对话必须逐字保留。
- 连续 3 次压缩后，人物设定/关系状态矛盾数 = 0。

## 2. OpenHands

仓库：`OpenHands/software-agent-sdk`（condenser 已从主仓库迁到这里）

关键文件：

- `openhands-sdk/openhands/sdk/context/condenser/llm_summarizing_condenser.py` → `LLMSummarizingCondenser`
- `openhands-sdk/openhands/sdk/context/condenser/README.md`
- `openhands-sdk/openhands/sdk/context/condenser/prompts/summarizing_system.j2`
- `openhands-sdk/openhands/sdk/context/condenser/prompts/summarizing_events.j2`
- `openhands-sdk/openhands/sdk/context/condenser/base.py` → `RollingCondenser` / `CondensationRequirement`

### 触发条件

`get_condensation_reasons()` 返回三种原因：

1. `REQUEST`：`view.unhandled_condensation_request`，用户或 agent 显式请求。
2. `TOKENS`：`total_tokens > min(condenser.max_tokens, agent_llm.effective_max_input_tokens)`。
3. `EVENTS`：`len(view) > max_size`。

`condensation_requirement()` 的硬度：

- `TOKENS` → `HARD`（再发就真爆窗）。
- `EVENTS` → `SOFT`（只是历史管理，能压就压）。
- `REQUEST` → `HARD`。

默认参数：

```python
max_size = 240
max_tokens = None
keep_first = 2
minimum_progress = 0.1
hard_context_reset_max_retries = 5
hard_context_reset_context_scaling = 0.8
```

但默认 agent 用的 `default_condenser()` 是另一组：

```python
LLMSummarizingCondenser(llm=llm, max_size=80, keep_first=4)
```

所以“类默认 240/2”和“默认 agent 80/4”要分开看，别只抄一个数字。

### 切分与保留规则

`_get_forgotten_events()`：

- `REQUEST`：目标保留 `len(view) // 2` 条尾部。
- `EVENTS`：目标保留 `max_size // 2` 条尾部。
- `TOKENS`：目标把总 token 降到 `max_tokens // 2`，反推需要保留多少条尾部。
- 多个原因同时存在时取**最严格的**（保留最少）。

然后：

- `protected_prefix = keep_first`，并额外保证第一条 `SystemPromptEvent` 不被忘。
- `forgetting_start` 落在 `protected_prefix` 之后最近的可操作边界。
- `forgetting_end` 落在 `naive_end` 之后最近的可操作边界。
- 摘要插入位置 `summary_offset = forgetting_start`。

`hard_context_reset()`：

- 保留 leading system prompt，摘要其余全部。
- 如果摘要 LLM 报错（通常是摘要输入本身爆窗），把每条 event 字符串的最大长度按 0.8 逐次缩短，最多重试 5 次。

这套是**事件日志 + 墓碑**模型：

- 原始事件不删除，只追加 `Condensation`，记录 `forgotten_event_ids`、`summary`、`summary_offset`。
- `View` 每次从全量事件重放，应用所有 `Condensation`，得到当前上下文。
- 上一版摘要本身也是一个 event，下一次压缩会被再次摘要，所以是“滚动摘要”。

### 摘要 prompt 的关键约束

`summarizing_system.j2`：

- `USER_CONTEXT`：用户需求、目标、澄清。
- `TASK_TRACKING`：活跃任务、**精确的任务 ID 和状态**。
- `COMPLETED` / `PENDING` / `CURRENT_STATE`。
- 代码任务额外要求 `CODE_STATE`（文件路径、函数签名、数据结构）、`TESTS`（失败用例、报错、输出）、`CHANGES`、`DEPS`、`VERSION_CONTROL_STATUS`。
- 明确 `PRIORITIZE` 和 `SKIP`，要求按任务类型裁剪，不无关细节全塞。

`summarizing_events.j2` 把每条事件包成 `<EVENT>...</EVENT>`，最后一句是 `Now summarize the events using the rules above.`。

注意：它**不要求引用行号**，只要求文件路径、函数签名、任务 ID、错误信息。

### ObservationMaskingCondenser

当前 `software-agent-sdk` 的 condenser 目录里已经找不到 `ObservationMaskingCondenser` 源文件；第三方对 commit `bf769d1` 的审读记录了旧行为：

- 每个 step 都执行。
- 保留最近 `attention_window`（默认 5）条 observation。
- 更老的 observation 内容替换成 `<MASKED>`，但保留事件结构和 action/tool-call 骨架。

这条只能算**二手代码审读**，降权。它对我们有用的点不是 `<MASKED>`，而是“保留结构、只挖掉大块工具输出”的思路；纯聊天没有工具输出，可直接跳过。

### 已知 issue / 踩坑

- [#19337 Default condenser keep_first pins the first user message, so a later task loses to the original one](https://github.com/OpenHands/OpenHands/issues/19337)：`keep_first=2` 把“第一条用户消息”永久钉住，后来换任务时，摘要里已经是新目标，但原始旧任务仍在头部，模型容易继续做旧任务。
- [#1395 Condensation summary can be inserted between action and observation](https://github.com/OpenHands/software-agent-sdk/issues/1395)：摘要插入点落在 action/observation 之间，破坏 LLM API 的消息顺序。
- [#1496 Optimize the memory condenser to reuse cached multi-turn messages](https://github.com/OpenHands/software-agent-sdk/issues/1496)：摘要请求是全新 prompt，没复用已有缓存，压缩一次很贵。
- [#13425 Set max tokens for condenser in settings](https://github.com/OpenHands/OpenHands/issues/13425)：`max_tokens` 触发阈值长期不可配。

### 可借用点

- **append-only 原始日志 + 墓碑**：摘要只是视图，原始消息永远可回滚、可审计。
- `keep_first` 保护 system prompt，而不是保护“第一条用户消息”。
- token 压力是硬触发，事件数/轮数是软触发，两者分开。
- `minimum_progress=0.1`：一次至少压掉 10%，否则认为这次压缩没意义，避免空转。
- 硬重置时按 0.8 缩短摘要输入并重试，是处理“摘要本身爆窗”的实用兜底。
- 结构化摘要字段（USER_CONTEXT / TASK_TRACKING / CURRENT_STATE）适合改造成聊天版。

### 不采用的原因

- 事件/工具调用模型对纯聊天过重，QQ bot 没有 action/observation 对。
- `keep_first=2` 钉死第一条用户消息，会压制后续新话题。
- 摘要会被再次摘要，长会话里仍有 drift 风险；需要额外的“原文引用”锚点。
- 默认 agent 的 80 条事件上限对聊天轮次太少。

### 可量化判据

- 原始消息保留率 100%，任意一条可按 ID 回滚。
- 摘要插入后，消息顺序合法率 100%，0 个 orphan tool pair。
- 连续 3 次压缩后，任务 ID/状态字段保留率 100%。
- 压缩后 20 轮内，旧任务复燃率 < 5%。

## 3. Cline / Roo-Code

### 3.1 Cline 旧版规则截断（v3.76）

仓库：`cline/cline`

关键文件：

- `src/core/context/context-management/ContextManager.ts`
- `src/core/context/context-management/context-window-utils.ts`

#### 触发条件

`shouldCompactContextWindow(clineMessages, api, previousApiReqIndex, thresholdPercentage?)`：

```ts
const totalTokens = (tokensIn || 0) + (tokensOut || 0) + (cacheWrites || 0) + (cacheReads || 0)
const { contextWindow, maxAllowedSize } = getContextWindowInfo(api)
const roundedThreshold = thresholdPercentage
  ? Math.floor(contextWindow * thresholdPercentage)
  : maxAllowedSize
const thresholdTokens = Math.min(roundedThreshold, maxAllowedSize)
return totalTokens >= thresholdTokens
```

`getContextWindowInfo()` 的 `maxAllowedSize`：

- 64k 窗口：`window - 27_000`
- 128k：`window - 30_000`
- 200k：`window - 40_000`
- 其他：`max(window - 40_000, window * 0.8)`

也就是实际在 **80%–90%** 附近触发，取决于窗口大小。

#### 切分与保留规则

`getNextTruncationRange(apiMessages, currentDeletedRange, keep)`：

- 永远保留第 0、1 条（第一条 user + 第一条 assistant）。
- 从 `startOfRest` 开始，只删偶数条，保持 user-assistant-user-assistant。
- `keep = "half"`：删 `floor((len - startOfRest) / 4) * 2` 条。
- `keep = "quarter"`：删 `floor(((len - startOfRest) * 3) / 4 / 2) * 2` 条。
- 删除区间末尾必须是 assistant，否则回退一条。
- `none` 删光第一对之后全部；`lastTwo` 额外保留最后 user-assistant 对。

`getNewContextMessagesAndMetadata()` 的选择：

```ts
const keep = totalTokens / 2 > maxAllowedSize ? "quarter" : "half"
```

也就是“删一半还不够，就删四分之三”。

删除不是物理删除，而是记录 `conversationHistoryDeletedRange: [start, end]`，发送前用 `getAndAlterTruncatedMessages()` 拼成“第一对 + 区间之后的尾部”，并清理 orphan `tool_result`、重排 `tool_use` / `tool_result`。

#### 环境详情裁剪

Roo-Code 的 `src/core/environment/getEnvironmentDetails.ts` → `getEnvironmentDetails(cline, includeFileDetails)` 是另一条线，但裁剪手法很实用：

- 可见文件：`slice(0, maxWorkspaceFiles)`，默认 200。
- 打开的 tab：`slice(0, maxTabs)`，默认 20。
- 只保留 busy/inactive terminal 的**未取回输出**，并用 `Terminal.compressTerminalOutput()` 压缩。
- 最近修改文件单独一节。
- 当前时间、git status、cost、mode/model。
- `includeFileDetails` 时才列工作区文件；`maxFiles === 0` 直接禁用。
- 所有内容包在 `<environment_details>...</environment_details>` 里。

这不是聊天摘要，但“硬上限 + 只给未取回的新信息 + XML 包裹”可以直接借到 QQ 的“群聊环境/最近消息”注入。

### 3.2 Cline 新一代 agentic compaction

仓库：`cline/cline`

关键文件：

- `sdk/packages/core/src/extensions/context/agentic-compaction.ts` → `runAgenticCompaction()`
- `sdk/packages/core/src/extensions/context/compaction-shared.ts` → `findCutIndex()` / `buildSummaryRequest()` / `ensureFilesSection()`

#### 触发条件

`compaction-shared.ts` 的常量：

```ts
CONTEXT_WINDOW_INPUT_RATIO = 0.9
COMPACTION_TRIGGER_RATIO = 0.9
DEFAULT_TARGET_RATIO = 0.7
DEFAULT_PRESERVE_RECENT_TOKENS = 20_000
DEFAULT_SUMMARY_MAX_OUTPUT_TOKENS = 8_192
TOOL_RESULT_CHAR_LIMIT = 2_000
FILE_CONTENT_CHAR_LIMIT = 2_000
```

可理解为：可用输入预算 = 窗口 × 0.9；用到可用预算的 90% 触发；压缩后目标 = 原预算的 70%；最近 20k token 逐字保留。

#### 切分与保留规则

`findCutIndex(messages, preserveRecentTokens, estimateMessageTokens)`：

1. 从尾部往前累加，直到 ≥ `preserveRecentTokens`，得到候选切点。
2. **绝不切掉最新的用户输入**：如果存在最新的 typed user turn，切点不晚于它。
3. 从候选切点继续往前退，直到落在安全边界：`assistant` 或“用户轮次开始”；`tool_result`-only 的 user 消息永远不作为切点，避免拆散 tool_use/tool_result。

`runAgenticCompaction()`：

- `messagesToSummarize = messages.slice(0, cutIndex)`
- `latestSummaryIndex = findLatestSummaryIndex(messagesToSummarize)`
- `newMessagesToFold = latestSummaryIndex >= 0 ? messagesToSummarize.slice(latestSummaryIndex + 1) : messagesToSummarize`
- 也就是说：**上一版摘要之前的内容不再重摘，只把新增消息折进摘要**。
- `extractFileOps()` 从消息里抽读过的文件、改过的文件；`ensureFilesSection()` 在摘要末尾强制补 `## Files`。
- 结果消息 = `buildSummaryMessage(...)` + `messages.slice(cutIndex)`。

`buildSummaryRequest()` 的 prompt 结构：

```text
Summarize this session for continuation. Be concise and factual.
## Goal
One sentence: what is being built or fixed.

## State
- Done: completed steps
- In Progress: current work
- Blocked: blockers or open questions

## Highlights
Key technical choices or notable findings (omit if none).

## Next
Immediate next steps.
## Files
Read: ...
Edited: ...
```

如果有 `previousSummary`，追加：

```text
Previous summary:
...
```

然后是 `Conversation:` 原文。

`buildSummaryMessage()` 的 metadata 里带 `kind: "compaction_summary"`、`userRunSpan`、`tokensBefore`、`generatedAt`、`details.readFiles/modifiedFiles`。这让下一轮能识别“这是一条摘要”，而不是普通 user/assistant 消息。

#### 摘要 prompt 的关键约束

- 简洁、事实性。
- 必须有 Goal / State / Highlights / Next / Files。
- State 区分 Done / In Progress / Blocked。
- 上一版摘要作为上下文传入。
- 文件列表由代码侧 `ensureFilesSection()` 兜底，不能只靠模型自觉。

#### 已知 issue / 踩坑

- [#5790 Automatic chat compacting at 160k tokens loses critical context and causes Cline to restart completed work](https://github.com/cline/cline/issues/5790)：压缩后模型重做已完成工作。
- [#5616 New context condensing feature causes excessive token burning and context loss](https://github.com/cline/cline/issues/5616)：压缩后新会话几秒又满，token 燃烧。
- [#8287 Cline refusing to start coding with gpt5.x](https://github.com/cline/cline/issues/8287)：`summarize_task` 工具不可用时，模型陷入“只能总结”的死循环。
- [#14732 Agentic compaction installs a truncated summary silently when incompleteReason is set](https://github.com/cline/cline/issues/14732)：provider 返回不完整摘要，代码仍然安装，静默丢信息。
- [#9599 Cline will condense near 200k even in 1M context model](https://github.com/cline/cline/issues/9599)：阈值没有跟随窗口缩放。
- [#14329 Auto-compact threshold scales with context window, so 1M-context models never compact in practice](https://github.com/cline/cline/issues/14329)：另一个方向的阈值问题，说明“阈值必须可观测、可配置”。

### 3.3 Cline `summarize_task` 的聊天可借部分

`src/core/prompts/contextManagement.ts` 的 `summarizeTask()`：

- 只给模型两个选项：`attempt_completion` 或 `summarize_task`。
- 明确“你只能通过 summarize_task 回复，否则会失去除摘要外的所有消息”。
- 要求先在 `<thinking>` 里按时间顺序分析，再输出摘要。
- 固定 10 个 section：Primary Request and Intent / Key Technical Concepts / Files and Code Sections / Problem Solving / Pending Tasks / **Task Evolution** / Current Work / Next Step / Required Files / 最近用户消息。
- `Task Evolution` 要求保留原始任务、后续修改、当前活跃任务，并**引用用户原话**解释为什么改。
- `continuationPrompt(summaryText)` 明确让模型“从断点继续，不要问用户任何问题”。

这套 10 段结构对 QQ bot 太重，但“Task Evolution + 引用原话”可以直接改成“话题演变 + 用户原话”。

### 可借用点

- token 触发用“可用预算”而不是裸窗口，且留 20k 尾部。
- 切点必须在用户轮次边界，不能切在对话中间。
- **只折叠上一版摘要之后的新消息**，这是防止 double summary / summary drift 的关键。
- 摘要 metadata 标记 `kind`，下一轮可识别，不会把摘要当普通聊天。
- 文件/操作列表由代码侧兜底追加，不信任模型自觉。
- 压缩前有 checkpoint，可回滚。

### 不采用的原因

- 旧的 `getNextTruncationRange` 是纯删除，不摘要，长期会丢上下文。
- 环境详情裁剪是 IDE 场景，QQ 没有 VSCode 可见文件/tab/terminal。
- `summarize_task` 的 10 段和工具约束对纯聊天过重。
- 1M 窗口下的阈值事故说明不能把“窗口比例”写死。

### 可量化判据

- 触发点落在可用预算的 75%–85%，不得 > 90%。
- 最近 20k token 或最近 10 个用户轮次逐字保留。
- 摘要输出 ≤ 8k token；超过则截断并告警。
- `covered_until` 单调递增，同一 message ID 被摘要次数 = 1。
- 压缩后 10 轮内重做已完成任务的比例 < 5%。

## 4. Letta / MemGPT

仓库：`letta-ai/letta`

注意：当前 README 指向 `letta-ai/letta-code`，老的 Python 服务端在 `archive` 分支。下面是 archive 分支源码，属于“历史实现”，但机制仍是 MemGPT 系的标准做法。

关键文件：

- `letta/services/summarizer/summarizer.py` → `Summarizer.summarize()` / `_partial_evict_buffer_summarization()` / `simple_summary()`
- `letta/services/summarizer/summarizer_all.py` → `summarize_all()`
- `letta/services/summarizer/summarizer_config.py` → `CompactionSettings`
- `letta/constants.py` → `SUMMARIZATION_TRIGGER_MULTIPLIER`
- `letta/agents/letta_agent_v3.py` → `compact()` 触发点
- `letta/prompts/summarizer_prompt.py` → `ALL_PROMPT` / `SLIDING_PROMPT` / `SELF_*`

### 触发条件

`letta/constants.py`：

```python
SUMMARIZATION_TRIGGER_MULTIPLIER = 0.9
```

`letta_agent_v3.py` 在每个 step 结束后：

```python
if self.context_token_estimate is not None and self.context_token_estimate > compaction_trigger_threshold:
    summary_message, messages, summary_text = await self.compact(...)
```

也就是上下文估算用量超过窗口的 90% 时触发。`compaction_trigger_threshold` 由窗口 × 0.9 得到。

`CompactionSettings` 默认：

- `mode = "sliding_window"`
- `clip_chars = 50000`
- `prompt_acknowledgement = False`
- `sliding_window_percentage` 默认取 `summarizer_settings.partial_evict_summarizer_percentage`（默认 0.30）

`Summarizer` 默认：

- `message_buffer_limit = 10`
- `message_buffer_min = 3`
- `partial_evict_summarizer_percentage = 0.30`

`MessageManager` 层还有一套更大的默认：`message_buffer_limit=60`、`message_buffer_min=15`。

### 切分与保留规则

`sliding_window` 模式：

```python
target_message_start = round((1.0 - self.partial_evict_summarizer_percentage) * total_message_count)
```

默认 0.30 意味着 **保留尾部约 30%，摘要前面约 70%**。然后从 `target_message_start` 往后找第一条 assistant，切成：

- 保留：`all_in_context_messages[assistant_message_index:]`
- 摘要：`all_in_context_messages[1:assistant_message_index]`
- 结果：`[system_message, summary_message, *kept_tail]`

摘要消息的角色是 `user`，插入在 index 1，紧跟 system 之后。

`all` 模式：

- 摘要 `in_context_messages[1:-1]`，保留最后一条。
- 如果最后一条是 `approval`，保护它和同一 step 的前一条 assistant。
- 返回 `[system, protected_messages]`。
- 摘要超过 `clip_chars=50000` 就硬截断，并加 `SUMMARY_TRUNCATION_SUFFIX`。

`simple_summary()` 会把消息转成紧凑纯文本 transcript：

```text
<start_transcript>
[user] ...
[assistant] ...
<end_transcript>
. Generate the summary.
```

工具返回默认截到 `TOOL_RETURN_TRUNCATION_CHARS`；如果摘要本身爆窗，还有 `middle_truncate_text()` 做“保留头 30% + 尾 30%、中间挖掉”的降级。

### 摘要 prompt 的关键约束

`ALL_PROMPT`（≤500 词）和 `SLIDING_PROMPT`（≤300 词）要求：

- `High level goals`：高层目标、用户明确请求；如果 transcript 里已有旧摘要，要继续沿用，不能丢长期进度。
- `What happened`：谁说了什么、做了什么、怎么推进；如果旧摘要正在被驱逐，要从中提取关键信息。
- `Important details`：文件、代码段、计划文件、GitHub issue/PR、Linear ticket。
- **Preserve identifiers verbatim**：计划文件名/路径、完整 URL、issue/PR 编号、ticket ID，不得转述或截断。
- **Preserve referenced identifiers unless explicitly resolved**：除非有明确证据已失效，否则保留。
- `Errors and fixes`：错误、修复、用户反馈；有用的话保留用户原话。
- `Current state`：最近在做什么，带文件名和代码片段。
- `Optional Next Step`：下一步，必须和最近用户请求直接相关；附最近对话原话。
- `Lookup hints`：放不进摘要的长内容，记主题和关键词，方便以后回查消息历史。
- 第一人称、事实记录；只输出摘要。

`SELF_*` 变体额外要求：

- `Do NOT continue the conversation.`
- `Do NOT respond to any questions in the messages.`
- `Do NOT call any tools.`
- 只输出摘要文本。

### 已知 issue / 踩坑

- [#506 MemGPT gets stuck thinking forever](https://github.com/letta-ai/letta/issues/506)：摘要后仍然爆窗，出现 `message length 16 -> 6` 后继续 `Request exceeds maximum context length`，然后反复摘要。
- [#3119 Conversation summarization fails with lmstudio](https://github.com/letta-ai/letta/issues/3119)：摘要请求自己撞上下文窗口，`summarize_all` 失败。
- [#2564 Google AI error on summarize](https://github.com/letta-ai/letta/issues/2564)：provider 兼容性问题导致摘要调用直接抛错。

这些问题的共同点是：**摘要器本身也会爆窗，必须有降级路径**。

### 可借用点

- 90% 触发，给正常回复留 10% 余量。
- 摘要插入 index 1，紧跟 system，结构稳定。
- 500/300 词的硬上限，防止摘要膨胀成第二份历史。
- “保留标识符 verbatim” + “lookup hints” 是聊天摘要最实用的两个字段。
- `Previous summary` 参与下一次摘要，形成滚动摘要。
- 摘要失败时有 middle-truncate / 工具返回截断 / 重试降级。

### 不采用的原因

- 默认保留 30%、摘要 70% 对聊天太激进，容易丢最近话题。
- 摘要以 `user` 角色插入，长人格聊天里模型可能把摘要当成用户说的话，产生角色混淆。
- 50k 字符上限太大，实际会挤占主上下文。
- `message_buffer_limit=60` 是消息条数，不是 token，长消息会失真。

### 可量化判据

- 压缩后尾部逐字保留 ≥ 最近 30% token 或 ≥ 10 个用户轮次。
- 摘要 ≤ 500 词（中文按 800 字折算）。
- 标识符（人名、日期、数字、URL、承诺）保留率 ≥ 95%。
- 连续 3 轮内重复触发压缩次数 = 0。
- 摘要调用失败时，主回复成功率 100%（降级不阻塞）。

## 10. 给 QQ 纯聊天 bot 的机制设计

目标：长期陪聊不断片、不爆窗、不把人格聊丢、不因摘要失败卡住回复。

### 10.1 三层结构

1. **原始日志层**：所有消息 append-only 落盘，带 `message_id`、`chat_id`、`sender_id`、`timestamp`、`reply_to`。永远不删。
2. **滚动摘要层**：一条 `rolling_summary`，带 `covered_until_message_id`，只覆盖到某个高水位。
3. **固定层**：system prompt、人格设定、关系状态、 pinned facts（用户明确说“记住”的内容）。这一层不参与摘要，永远原样注入。

发送给模型的上下文：

```text
[system: 人格 + 固定关系 + pinned facts]
[system: rolling_summary（如果存在）]
[最近 N 轮原始消息]
[当前用户消息]
```

摘要不要用 `user` 角色，建议用 `system` 或专门的 `context_summary` 段，避免模型把摘要当成用户说的话。

### 10.2 触发

- 软触发：每轮 assistant 回复结束后估算 token，达到**可用预算的 75%** 时，后台开始生成摘要；不阻塞当前回复。
- 硬触发：达到 **90%** 时，必须压缩；如果摘要还没好，先做确定性裁剪（丢最老的 1/4 轮次）保证回复。
- 轮数兜底：即使 token 没到，连续 40 轮也压一次，防止短消息堆积。
- 只在一轮结束后触发，绝不在用户消息和 assistant 回复之间切。

可用预算 = 模型窗口 − 输出预留（建议 20% 或 8k，取较大者）。

### 10.3 切分

- 头部保护：system + 人格 + pinned facts，不参与摘要。
- 尾部保护：最近 20k token 或最近 10 个用户轮次，取较大者；尾部必须从用户轮次开始。
- 中间段：`covered_until` 之后、尾部保护之前的所有消息，送摘要。
- 不保护“第一条用户消息”。这是 OpenHands #19337 的教训：旧任务会压住新任务。真正该保护的是人格和 pinned facts。

### 10.4 摘要链

- 读取上一版 `rolling_summary` 和 `covered_until_message_id`。
- 只把 `covered_until` 之后、切点之前的**新增消息**折进摘要。
- 摘要完成后，`covered_until` 推进到切点前一条。
- 同一 message ID 永远只被摘要一次；如果发现重复覆盖，直接告警并跳过。

这是 Cline 新版最值得抄的一点：**不是每次重摘全史，而是旧摘要 + 新增消息**。

### 10.5 聊天摘要 schema

建议固定字段，控制在 800 字以内：

```text
[CONTEXT_SUMMARY v1]
covered_until: <message_id>

OPEN_THREADS:
- 还没聊完的话题，最多 5 条

USER_FACTS:
- "用户原话"（msg_id, 日期）

RELATIONSHIP:
- 当前关系/称呼/边界/最近情绪

COMMITMENTS:
- 谁答应了什么，截止时间

UNRESOLVED:
- 未解决的问题、待确认的事

RECENT_TONE:
- 最近几轮的语气、玩笑、敏感点

LOOKUP_HINTS:
- 放不进摘要的长内容关键词
```

硬约束：

- 人名、称呼、日期、数字、地点、承诺必须逐字保留。
- 用户原话至少保留 3 条，带 `msg_id`。
- 不写推测，不写建议，不写“作为 AI”。
- 不续写对话，不回答消息里的问题。
- 摘要长度超过上限就截断并标记 `[TRUNCATED]`，不能静默。

### 10.6 失败与防循环

- 摘要调用失败：保留最近 20k token，丢弃更老的中间段，插入一行 `[较早聊天已省略]`，保证回复。
- 摘要返回空/缺字段/长度异常：重试一次，用更严格的 prompt；再失败就降级裁剪。
- 连续 2 次压缩间隔 < 3 轮：判定为抖动，暂停自动压缩 10 轮，只做确定性裁剪。
- 摘要后 token 反而没降：回滚到压缩前，记录告警。
- 摘要 provider 报 `incompleteReason`：不要安装这条摘要（Cline #14732 的教训）。

### 10.7 观测指标

每条都落日志，便于回归：

- `tokens_before` / `tokens_after` / `compression_ratio`
- `covered_until` / `messages_summarized` / `messages_preserved`
- `summary_tokens` / `summary_latency_ms`
- `trigger_reason`（soft/hard/turn）
- `summary_failed_reason`
- `fact_recall_probe`（定期用固定问题测）

## 11. 可量化验收

建议直接拿这 6 条做验收，不要只看“感觉没丢”：

1. **事实召回**：200 轮合成聊天，植入 50 条事实（人名、日期、偏好、承诺），压缩后随机抽 20 条提问，召回 ≥ 90%。
2. **人格稳定**：连续 5 次压缩后，system/pinned facts 矛盾数 = 0；称呼、关系边界不被摘要改写。
3. **触发精度**：软触发落在可用预算 75%±5%，硬触发 ≤ 90%；1000 轮压测 0 次 context overflow。
4. **保留尾部**：最近 20k token 或最近 10 个用户轮次逐字保留；切点 100% 落在用户轮次边界。
5. **成本与延迟**：摘要调用 ≤ 每 20 轮 1 次；摘要成本 ≤ 总 token 的 5%；P95 延迟 ≤ 2.5s，且不阻塞当前回复。
6. **防重复**：同一 `message_id` 被摘要次数 = 1；连续 3 轮内重复压缩 = 0；摘要失败时主回复成功率 100%。
