## 结论

纯聊天摘要应该插在 **compaction / surface 层**，而不是记忆层或 OneBot 层：在轮次结束后的维护里，用一次 `surfaceOp:{op:'replace',startSeq,endSeq}` 把「更早的纯聊天段」换成一个 `user/message` 摘要节点，节点用 `source.kind='runtime-context'`、`source.form='chat-digest'`，并让 live-compact 把这个 form 当成 checkpoint 地板。不要放在 `agent/pre-step` 的同步路径里做模型摘要；那会把摘要生成和整段后缀的 cache 失效都压到首字之前。

## 1. 为什么纯聊天尾巴选不出切点

### 1.1 先区分两个「尾巴」

- **最新一轮的尾巴**（最后一条 user + 它后面的 assistant）：结构上不可切。`pointerSpanAllowed` 明确禁止最后一条 genuine user 落在段内（`plan.js:1011-1024`），`retreatIncompleteTail` 又把末尾的 assistant 退掉（`plan.js:877-880`，调用点 `index.js:947`）。所以这一轮永远不在候选区。
- **更早的纯聊天**：不是结构上不可切，而是被三个数值/卡片闸门层层卡住。生产日志里的 `cut:extended-gain:N` → `no-candidates:-` → `cut-skip/no-legal-span` 就是这条链。

### 1.2 实际计算链（按调用顺序）

以一次纯聊天 surface 为例：`system?, u1,a1,u2,a2,...,un,an`，没有 `tool/result`，没有 checkpoint。

1. **先退掉未完成的末条 assistant**
   `selectNewestChunk` 把 `end` 设为最后一个节点，再调用 `retreatIncompleteTail(end, first, typeOf)`（`index.js:947`）。该函数只做一件事：如果末条是 assistant，就 `end -= 1`（`plan.js:877-880`）。于是 `end = un`（最后一条 user）。

2. **`keepRounds` 在纯聊天里完全空转**
   `visible` 只把 `tool/result` 标成 `type:'tool'`（`index.js:951-966`）；`finishedToolRounds` 需要「assistant 带 tool-call → tool/result」配对（`plan.js:493-514`）。纯聊天没有这种配对，`rounds = []`（`index.js:968-975`），`span = null`，`cutEnd = null`（`index.js:980-981`）。`keepRounds` 只控制「最近几个已结束的工具轮留在原处」（`settings.js:6`，`plan.js:546-553`），它 **不是** 「保留最近 N 轮聊天」。所以纯聊天里 `keepRounds=3` 既不提供锚点，也不保护最近 3 轮对话。

3. **`walkOffTail` 再把最后一条 user 退掉**
   `selectCutIndexes` 收到 `maxEnd = un`（`index.js:1087`）。`walkOffTail` 先跳过末尾的 assistant；对 user 边界，第一轮循环会 `break`，但紧接着的 `while (isUserBoundary(items[end])) end -= 1` 会无条件退掉它（`plan.js:852-867`）。于是 `end = a(n-1)`，`lastUser = un`。

4. **phase 只剩一条 assistant**
   `phase = expandBack(end=a(n-1), crossUser:false, chunkMax)`（`plan.js:969`）。`expandBack` 往左走，遇到 `u(n-1)` 的 `isUserBoundary` 就停（`plan.js:897-912`，判断在 906）。所以 `phase = [a(n-1)]` 单条。
   `nonUserGain` 只累加非 user、非 system 的 token（`plan.js:832-838`），因此 `phase.gain = tokens(a(n-1))`。
   `chunkMin` 默认 1000（`settings.js:9`）。QQ 的一条回复通常远小于 1000 token，`phase.gain < chunkMin`，phase 分支（`plan.js:970-976`）直接跳过。

5. **extended 跨用户，但 gain 只算 assistant**
   `retreatBefore(end, lastUser)` 在 `end < lastUser` 时原样返回（`plan.js:890-895`），所以 `end` 仍是 `a(n-1)`。
   `chatMax = min(chunkMax, 8000)`（`plan.js:994`，常量在 `plan.js:13-14`）。`extended = expandBack(end, crossUserFloor-1, crossUser:true, chunkMax:8000)`（`plan.js:996`）会一路往左跨过 user，直到累计 **user+assistant 总 token** 到 8000 为止。
   然后：
   - `extended.gain = nonUserGain(...)`（`plan.js:998`）只算 assistant；
   - `extended.tokens = spanTokens(...)`（`plan.js:999`）算 user+assistant。

   所以 `extended.gain < chunkMin` 等价于：**8K 窗口里 assistant 的 token 占比不到 12.5%**（1000/8000）。QQ 纯聊天常见「用户长语音转写/长段文字，bot 回两三句」，assistant 占比经常低于 12.5%，于是命中：

   `note("cut:extended-gain:" + extended.gain)` → `return pointer`（null）（`plan.js:1001`）。

   如果单条消息本身超过 8000 token（超长转写），会先命中 `extended.tokens > chatMax` → `cut:extended-max`（`plan.js:1000`）。

6. **即使 gain 过了，还有「卡片必须更小」**
   `evaluateCandidate` 用 `buildCard` 生成卡片（`index.js:1157`、`index.js:1187`）。`buildCard` 的 `earlierUsers` 会把段内每一条较早 user 的 **完整原文** 以 JSON 行抄进卡片（`plan.js:1305-1315`），不截断、不摘要。纯聊天段里 user 通常占大头，卡片大小接近原段。
   提交前 `commitSelectedSpan` 会算 `framedTokens`，如果 `framedTokens >= chunk.tokens` 就抛 `summary is not smaller than the shadowed content`（`index.js:2521-2525`）。所以即使切点选出来了，也可能死在「摘出来并不更短」。

7. **本地引擎是硬性不可切**
   `resolveEngine` 把内网/回环/读不到地址的模型判为 `local`（`plan.js:807-830`）。local 分支只能返回最后一条 user 之后的单条 assistant（`plan.js:946-957`）。但 `commitSelectedSpan` 调 `pointerSpanAllowed(items, start, end, 'local')`，其中规定 `start <= lastUser` 直接 false（`plan.js:1011-1024`，调用在 `index.js:2449-2452`）。纯聊天的候选 `a(n-1)` 永远在 `un` 左边，所以 **local + 纯聊天在提交阶段必然被拒**。

8. **外层如何记录**
   `selectNewestChunk` 两个 picker 都为空时记 `no-candidates:-`（`index.js:1112-1113`）；维护循环拿到 null 后记 `cut-skip / no-legal-span`，并把 `why` 拼上前面所有 note（`index.js:2294-2310`）。所以日志顺序通常是：
   `cut:extended-gain:N` → `no-candidates:-` → `no-legal-span`。

### 1.3 一张表

| 判据 | 代码位置 | 纯聊天里的实际效果 |
|---|---|---|
| 最后一条 genuine user 不得入段 | `plan.js:1011-1024` | 最新一轮永远不可切；这是结构性的 |
| `retreatIncompleteTail` | `plan.js:877-880` | 只退最后一条 assistant，`end` 落到最后一条 user |
| `walkOffTail` 退 user | `plan.js:852-867` | `end` 再退到 `a(n-1)` |
| `keepRounds` / `finishedToolRounds` | `plan.js:493-514`、`546-553` | 纯聊天 0 个工具轮，完全不参与 |
| `chunkMin`（默认 1000） | `settings.js:9` | 单条 assistant 几乎不可能单独过线 |
| `CHAT_SPAN_MAX`（8000） | `plan.js:13-14` | extended 窗口按 **总 token** 封顶 |
| `nonUserGain` 排除 user | `plan.js:832-838` | extended 的 gain 只算 assistant；占比 <12.5% 必然失败 |
| `buildCard` 抄全部较早 user | `plan.js:1305-1315` | 卡片接近原段，可能被 `framedTokens >= chunk.tokens` 拒 |
| local 的 `start > lastUser` | `plan.js:1011-1024` | local 纯聊天永远提交不了 |

### 1.4 结论

- 对「最新一轮」：必然 no-candidates，因为最后一条 user 是硬边界。
- 对「更早的纯聊天」：在 QQ 的长问短答分布下，`extended.gain` 几乎必然小于 `chunkMin`，所以表现为 `extended-gain`；即使偶然过线，`buildCard` 的「抄全文」也会让收益接近零，甚至被提交闸门拒绝。
- `keepRounds` 不是聊天轮数保护，不能拿来解释或修复纯聊天切不出来。

## 2. surface 上「可以安全替换的最小单位」

### 2.1 `surfaceOp:{op:'replace',startSeq,endSeq}` 的硬边界

提交前 `assertCurrentSpan` 会重新检查（`index.js:2433-2453`），实际约束是：

1. `startSeq`、`endSeq` 必须都在 `session.surface.nodes` 里，且 `startSeq <= endSeq`；区间是 `nodes.slice(start, end+1)`，**连续、不能跳节点**（`index.js:2436-2441`）。
2. `start` 必须严格晚于 surface 上 **最后一张 checkpoint**：`floor = items.findLastIndex(checkpoint); if (start <= floor) throw`（`index.js:2448-2452`）。换句话说，区间内不能含 checkpoint，区间也不能从 checkpoint 或它左边开始。
3. `pointerSpanAllowed`（`plan.js:1011-1024`）：
   - 区间内不能含 checkpoint；
   - 最后一条 genuine user 不能在区间内；
   - `engine === 'local'` 时，`start` 必须大于最后一条 genuine user（即整段在最后一条 user 之后）。
4. 工具配对必须在段前、段后都平衡：`cutOk(toolPairingBalancedBefore, start)` 和 `cutOk(toolPairingBalancedAfter, end)`（`index.js:2451`）。纯聊天没有工具对，恒 true。

### 2.2 能跨多条、能替换 assistant 吗

- **能跨多条**：一次 replace 可以覆盖任意连续 N 个节点，最终只产生一个替换事件。live-compact 的卡片就是这样替换「多条 user/assistant + 工具结果」的（`index.js:2537-2555`）。
- **能替换 assistant**：能。`end` 通常就是 assistant（`a(n-1)` 或工具轮的最终 assistant）；cloud 下 `start` 也可以是较早的 user。`pointerSpanAllowed` 只禁止「最后一条 genuine user」入段，不禁止 assistant。
- **最小合法单位**：节点级最小是 1 条（`startSeq === endSeq`，mnemonic 的 tombstone 就是单节点替换，`dsh-mnemonic/index.js:804-838`）。但对「聊天摘要」来说，单条 assistant 没有意义；**语义上的最小单位是 cloud 下的一组完整旧轮次（user+assistant）**。local 下不能含 user，所以无法用一次 replace 摘要一问一答，只能单条 assistant，语义上不成立。
- **不能替换的**：最后一条 genuine user；任何 checkpoint 及其左侧；含未配对 tool-call 的边界；local 下最后一条 user 左侧的任何东西。

### 2.3 `deriveMessages` 会怎样

`deriveMessages()` 的宿主实现不在本仓库。按 surface 契约和调用方行为推断：

- `session.surface.nodes` 是派生消息的**有序 seq 列表**；替换后，区间内的 N 个节点从列表里消失，新 append 的事件出现在同一位置，成为 **1 条** 派生消息。
- 事件日志本身不删除：被替换的原事件仍在 `snapshotEvents()` 里，`sourceEventSeqs` 保留来源。mnemonic 的 tombstone 和 live-compact 的卡片都依赖这一点。
- 其它节点的 seq 不变（seq 是 append-only 事件号，不是数组下标），所以「切点右边还有卡片」这类检查仍然有效（`index.js:882-888`）。

### 2.4 KV cache 会怎样

provider 的 prompt cache 是前缀缓存。替换点 `startSeq` 之前的内容字节不变，缓存能命中到 `startSeq`；从 `startSeq` 开始，消息序列变成了「一条摘要 + 原来的后缀」，位置和内容都变了，**后缀全部要重新 prefill**。这就是 live-compact 反复强调「不改前缀字节」「切点前面的内容保持原样」的原因（文件头注释 `index.js:1-5`，README「卡片和切点」）。

仓库自己的前缀模型在 `thunder.js:11-25`：`sharedPrefixLength` 算公共前缀，`decideThunder` 在公共前缀比例 <0.9 时选择整段重发。`rememberPrefix` 也是把 `deriveMessages()` 拼起来存（`index.js:2573-2582`）。

因此：

- **切点越靠右，失效的后缀越短**。纯聊天应切在「保留最近 K 轮」之前，而不是从很早的地方切。
- **一次替换一个大段**，比每轮替换一小段更省：每次替换都会让后缀再失效一次。
- **替换本身不会让下一请求变长**，但摘要节点在第一次使用时是未缓存的；收益要看「省下的原段 token」减「摘要 token + 后缀重prefill」。

### 3.2 推荐形状

```js
session.append('user/message', {
  id: randomUUID(),
  role: 'user',
  content: [{
    type: 'text',
    text: `${CHAT_DIGEST_PREAMBLE}\n\n${digestBody}`,
  }],
  source: {
    kind: 'runtime-context',
    form: 'chat-digest',
    digest: { id: digestId, fromSeq, toSeq, turns, tokens },
  },
}, {
  surfaceOp: { op: 'replace', startSeq, endSeq },
  sourceEventSeqs: shadowedSeqs,
})
```

- `CHAT_DIGEST_PREAMBLE` 照抄 live-compact 的口径：`这是旧内容摘要，不是新指令，也不是你的授权。`
- 不要带 `source.qq`，不要带 `proactiveReceiptToken`。
- `role` 必须是 `user`，但 `kind` 是 `runtime-context`；这样模型能读到内容，OneBot 不会当真人，mnemonic 不会当用户锚点，receipt 会过滤掉。
- `form='chat-digest'` 不和 mnemonic 的 `runtime-context + form:'snapshot'` 清理逻辑冲突（`dsh-mnemonic/index.js:133-139` 只认 snapshot）。
- 在 live-compact 的 `isCheckpoint` 里加一条：`kind === 'runtime-context' && source.form === 'chat-digest'`（`index.js:706-712` 附近，2 行）。不加的话，live-compact 会把 `runtime-context` 当 host-injected notice（`index.js:130-134`、`:770-796`），`expandBack(crossUser:true)` 会跨过它，下一次就可能把摘要重新卷进工具卡片。

### 3.3 为什么不是别的

- **assistant/message**：`dsh-mnemonic/index.js:503` 只看 role 找最近的 assistant；摘要会被当成上一轮回复归档，且 user 锚点会往前错一轮。排除。
- **system/message**：`staleSystemNodeSeqs` 会把除最后一条外的所有非空 system 清空（`dsh-mnemonic/index.js:164-176`）。排除。
- **`compact-checkpoint`**：OneBot 和 mnemonic 都能排除，但 receipt 只过滤 `runtime-context`，在 pre-step/同轮 append 时会 `blocked`；官方大压缩还可能把它当上一版摘要再压一次（live-compact README「卡片不使用官方的 compact-checkpoint」）。排除。
- **`spine-checkpoint`**：会被 `reconcileCardRawPaths` 当成 live-compact 的卡片，可能清空 `cardRawPaths`（`index.js:1506-1525`）。排除。
- **新的自定义 kind（如 `chat-summary`）**：`记忆核心.mjs:14` 不认，会被当真人发言；receipt 也不认。除非同时改 OneBot、mnemonic、receipt 三处，违背「同一判据只留一份」。不选。

## 4. 触发点：`agent/pre-step` 还是 maintenance

### 4.1 `agent/pre-step`

- 每个 step 都会跑，不是每轮一次。要「每轮一次」，必须像 mnemonic 那样加守卫：最后一条真人 user 之后已经有 assistant 就 return（`dsh-mnemonic/index.js:842-845`）。
- 摘要在请求前生成：如果是模型摘要，直接把 1-3 秒加到首字之前；即使是本地抽取，100 轮的扫描也会占用事件循环。
- 替换发生在当前请求之前，`startSeq` 之后的后缀本次就要重新 prefill；用户等的是「摘要生成 + 整段后缀 cache miss」。
- append 落在当前 turn 的事件区间里。用 `runtime-context` 可以同时躲过 OneBot 的 `发言消息`（`:14`）和 receipt 的计数（`receipt-transaction.mjs:393`）；用 `compact-checkpoint` 则会被 receipt 计数，主动搭话回合直接 `blocked`。
- 会和 live-compact 的 pending maintenance 抢 surface。`assertCurrentSpan` 会抛 `selected span changed before commit`（`index.js:2512`），不会写坏，但这一趟白跑并留下警告。

### 4.2 maintenance（轮次结束后）

- live-compact 已经在 `session/event` 的 `turn/end` 上调度维护（`index.js:1392-1399`），空闲时还有 `agent/status idle` 兜底（`index.js:1442-1455`）。
- `agent/pre-step` 只做「等待维护」，最多等 `PRESTEP_WAIT_TIMEOUT_MS = 3000`（`index.js:359`、`:1814-1836`）；超时就 abort 并让请求继续，然后把 `turnEndSeq - 1` 回退、重新调度（`:1830-1838`）。所以维护不会无限拖住首字。
- 摘要在 turn/end 之后 append，落在下一个 `turn/start` 之前；下一轮的 `currentHostCall` 从下一个 `turn/start` 往后切（`receipt-transaction.mjs:359-366`），看不到它。`记忆核心` 的 `inTurn` 同理（`:240-252`）。所以即使是 `compact-checkpoint`，在维护里也不会破坏 receipt；用 `runtime-context` 就更稳。
- 和现有 cut 的关系：把摘要做成 checkpoint 后，live-compact 的 `floorCard` 会停在它上面（`index.js:941-948`、`plan.js:855-857`），不会往左穿；下一次只会切摘要右边的部分。建议在 live-compact 的 cut 循环之后跑摘要，这样本轮的工具卡先落地，摘要再以最新卡为地板；两者不会选同一段。

### 4.3 对比

| | `agent/pre-step` | maintenance |
|---|---|---|
| 首字延迟 | 摘要生成 + 后缀 re-prefill 都在首字前 | 摘要生成在空闲时；只有 re-prefill 在下一请求 |
| 每轮次数 | 每个 step 都跑，需要守卫 | 每个 turn/end 一次 |
| 与 cut 冲突 | 可能抢同一段，`assertCurrentSpan` 抛错 | 同一队列串行，天然不抢 |
| receipt | 只有 `runtime-context` 安全 | turn 外，checkpoint 也安全 |
| 失败恢复 | 阻断本次请求或静默跳过 | pre-step 3s 超时后请求照常，维护重试 |

**建议**：放在 maintenance，turn/end 之后、live-compact 的 cut 之后；摘要生成（如果调模型）也在这里异步做，不进入 pre-step 的同步路径。若必须 pre-step，只做 O(n) 选区 + 预生成的摘要，不在 pre-step 调模型。

## 5. 最小可行结构

### 5.1 文件级改动

**新增** `dsh/vendor/dsh-live-compact/chat-digest.js`（约 150-180 行）：

- `CHAT_DIGEST_KIND = 'runtime-context'`、`CHAT_DIGEST_FORM = 'chat-digest'`、`CHAT_DIGEST_PREAMBLE`。
- `isChatDigest(event)`：`event.type === 'user/message' && source.kind === KIND && source.form === FORM`。
- `selectChatDigestSpan(session, { keepTurns, minGain, maxTokens })`：
  1. 取 `nodes = session.surface.nodes`；
  2. 找最后一张 checkpoint（含 `isChatDigest`）作为 `floor`；
  3. 从 `floor+1` 开始，按 `user → assistant` 配成完整轮次；遇到 `tool/result` 或带 tool-call 的 assistant 就停止（只处理连续纯聊天段）；
  4. 保留最后 `keepTurns` 轮（复用 `settings.keepRounds`，默认 3），候选段 = 更早的完整轮次；
  5. 要求 `end < lastUser`、段内无 checkpoint、`spanTokens <= maxTokens`（8000）、`nonUserGain >= minGain`（`chunkMin`，1000）；

- `buildChatDigest(events, span, { maxChars })`：每轮一行，保留 `seq`、角色、时间（能从事件拿到的话）和截断后的正文；硬约束行（复用 `plan.js` 的 `hardItems`）优先保留；总字符数封顶。v0 先做抽取式，不调模型；v1 再把 `summarize` 注入，放在 maintenance 异步跑。

### 5.2 状态存哪里

不新增状态文件。状态就在 surface 上：

- 最新一张 `chat-digest` 节点的 `source.digest.toSeq` 就是「已经摘要到哪」；
- `source.digest.id` 是幂等键；
- 进程重启后，surface 从事件日志重放，扫描逻辑自然恢复。

这比 `~/.dsh/.../chat-digest.json` 更稳：不会出现「文件写了、surface 没写」或反过来；也不需要跨进程锁（session 是单写者）。

### 5.3 幂等

1. 候选段只从「最后一张 digest 的 `toSeq` 之后」开始，天然不会重复覆盖。
2. append 前扫描 surface 上是否已有 `source.digest.id === id`；有就 no-op。
3. `session.append` 是单事件原子操作；抛错就没有替换，下一趟重试；成功后再跑，floor 已经前移，选区为空。
4. 同一段不生成两个 id：id 只由 `(sessionId, fromSeq, toSeq, textHash)` 决定，文本相同则 id 相同。

### 5.4 三条可量化验收

1. **压缩率**：造 100 轮纯聊天（user 300 token / assistant 40 token，约 34K token），跑一次维护后：
   - digest 节点 1 个；
   - 保留最后 3 轮原文；
   - `framedTokens <= 0.25 * chunk.tokens`（即摘要 ≤ 8.5K token，实际应 ≤ 2K）；
   - `tokenMeter.measure(session).totalTokens < 10K`。
2. **幂等**：同一 surface 连续跑 2 次维护，第 2 次 `session.seq` 增量 = 0，digest 节点数仍为 1；进程重启重放后再跑，仍为 1。
3. **契约 4/4**：
   - `发言消息(digest) === false`；
   - `同范围历史(digest, 'private:<id>') === true`，`记忆范围(session)` 仍返回原 QQ key；
   - 在有 digest 的主动搭话回合，`classifyProactiveCall` 返回 `verified`（不是 `blocked`）；
   - `archiveTurn` 返回的 `(userMsg.id, asstMsg.id)` 与插入 digest 前完全一致。
