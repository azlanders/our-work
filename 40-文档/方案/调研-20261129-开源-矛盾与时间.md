## 0. 先校正三个口径

### 0.1 这是开源线，不冒充学术线

任务书要求团队合计至少 5 篇论文；本文只负责开源实现线。下文所有“量化结果”分两种：

- **代码内固定参数**：例如候选 40 条、RRF `k=60`、8 条展开证据、4 轮扩展、8,000 token 审阅预算。这些是能复现的实现约束。
- **榜单/作者自测分**：只作为线索，不作为严格对照实验。CMB 各项目判分口径不同，不能直接相减。

没有在仓库里找到可复现端到端评测的，我会明确写“仓库未提供”，不拿 README 的宣传数字补空。

### 0.2 “版本”不是一件事

读完后最重要的校正：至少要把四种时间分开。

| 时间 | 回答的问题 | 典型字段 |
| --- | --- | --- |
| 事实生效时间 | 这件事从什么时候开始是真的 | `valid_at` / `validFrom` |
| 事实失效时间 | 这件事从什么时候开始不再是事实 | `invalid_at` / `validTo` |
| 系统写入/作废时间 | 系统是什么时候知道/处理这件事的 | `created_at` / `expired_at` / `supersededAt` |
| 说话时间 | 这句话是什么时候说出口的 | `spokenAt` / episode `reference_time` |

把“事实失效”和“系统作废”混成一个字段，会直接导致两类错误：

- 旧值在事实时间上还有效，却因为系统刚写入就被当成“已经过期”；
- 旧值在事实时间上早已失效，却因为系统写入时间更晚而被排在当前值前面。

Graphiti 把这两个时间拆成 `invalid_at` 和 `expired_at`；`dsh-mnemonic` 目前只有一个 `validTo`，且写入时取 `by.eventAt || by.createdAt || Date.now()`（`lib/store.js` 的 `supersede()`），事实时间和系统时间混在一起。这是本文最明确的落点之一。

### 0.3 “矛盾”不等于“后来提到”

Graphiti 和 Cognee 都明确禁止“仅因为更新、日期更晚、同一实体又出现”就判定旧事实作废：

- Graphiti `prompts/dedupe_edges.py`：只有新事实**明确让旧事实为假**才算矛盾；不能从 recency、会议日期、周报标题、同一实体的新活动推断。
- Cognee `review_conflicts.txt`：只有同一主体的同一属性出现**不能同时为真**的值才算冲突；计划/提议、同意异名、不同范围、需要未展示信息才能判断的，都不报。

这条规则直接对应 CMB 的“没解释的矛盾”和“真实变化”两类：模型不是缺一条“注意新旧”的提示，而是缺一个**可判定的作废判据**。

## 3. 逐个实现拆解

### 3.1 Mem0：从 DELETE 转向“只追加 + 链接”

**来源**

- `mem0/memory/main.py:881-1120` `_add_to_vector_store`
- `mem0/configs/prompts.py:468-730` `ADDITIVE_EXTRACTION_PROMPT`
- `mem0/configs/prompts.py:176-330` `DEFAULT_UPDATE_MEMORY_PROMPT`（旧版，当前主链路未使用）
- `mem0/configs/prompts.py:1007-1042` `_resolve_dates` / `generate_additive_extraction_prompt`
- `mem0/memory/main.py:1038` `attributed_to`

**机制**

当前 V3 的写入链路是：

1. 用新对话文本做向量检索，取 top 10 条 existing memory。
2. 把 UUID 映射成 `"0"`、`"1"` 这样的短标签，防止模型编造不存在的 ID（`main.py:925-935`）。
3. 一次 LLM 调用，system prompt 是 `ADDITIVE_EXTRACTION_PROMPT`；只允许 ADD，不允许 UPDATE/DELETE。
4. 输出 `text`、`attributed_to`、可选 `linked_memory_ids`；矛盾/更新通过链接表达，不删旧记录。
5. 按 `md5(text)` 去重，写向量库，写 history 事件 `ADD`。

旧版 `DEFAULT_UPDATE_MEMORY_PROMPT` 仍然定义了 ADD/UPDATE/DELETE/NONE，甚至明确写“新事实和旧事实矛盾就 DELETE”。但当前 `main.py` 只 import `ADDITIVE_EXTRACTION_PROMPT`，没有调用 `get_update_memory_messages`；这份提示词在这个快照里是遗留代码或兼容入口，不是 V3 主路径。

时间上，`ADDITIVE_EXTRACTION_PROMPT` 把 `Observation Date` 定义成“对话实际发生的时间”，要求所有相对时间都按它换算；`Current Date` 只作系统今天，明确不能拿来解释消息里的“昨天”。这避免了一个常见错误：回放旧对话时把“昨天”算成今天的前一天。

主体上，`attributed_to` 只分 `user` / `assistant`；`user_id`、`agent_id`、`run_id` 作为过滤维度。没有“第三个人”的实体 ID；多人对话里 assistant role 可能代表另一个人，提示词要求按 `name` 归属。

**量化结果**

仓库内没有可复现的 CMB 或 LoCoMo 跑分。代码内可量化的只有：existing memory top 10、单次抽取调用、`md5` 去重、`linked_memory_ids` 最多不设硬上限。本文不引用 README 的百分比。

**适用条件**

- 记忆主要是“用户事实/偏好/计划”，不是强一致性的参数表。
- 可以接受旧值留在库里，由检索/作答阶段处理新旧。
- 有稳定的 `user_id/agent_id/run_id` 过滤，避免跨用户污染。

**失败条件**

- 只追加意味着旧值永远不会被标成“不是现在”；如果检索把旧值排前面，模型仍会拿旧值当现在。Mem0 自己没解决这个问题，只是把“删”换成了“链接”。
- `linked_memory_ids` 是模型判断的相关性链接，不是当前值判定；链接存在不等于模型知道哪条是现在。
- `attributed_to` 只有 user/assistant 两档，第三人称事实容易归错。
- 抽取提示词很长，仍有“把上下文细节混进新事实”的风险；它用 `No Detail Contamination from Context` 规则防，但这是 prompt 约束，不是结构约束。

**可借用点**

- `Observation Date` 与 `Current Date` 分离，直接对应 `dsh-mnemonic` 的 `spokenAt` 和 `now`：相对日期换算只能用说话时间，不能用当前时间。
- “转变要写成 from X to Y”比“只记新值”更有用；CMB 的“真实变化”题需要旧值和新值同时在场。
- `linked_memory_ids` 的思路可以借，但不要只链接；要在渲染时把链接解释成“旧说法/现在的说法”。

**不采用的原因**

- 不采用“只追加、完全不判当前值”作为最终方案；它会把新旧冲突全部推给作答模型。
- 不采用旧版 DELETE；CMB 里“我以前叫什么”这类题需要旧值可查，物理删除会直接丢证据。
- 不采用 `attributed_to` 二值主体；我们需要至少“他/我/别人/助手”四类。

**实测判据**

- 在 47 道“没解释的矛盾”上，只加链接、不加当前值标记，预期几乎不涨；如果涨，说明检索排序本身已解决，不用上冲突结构。
- 在 58 道“真实变化”上，要求答案同时出现旧值和新值；只答新值算半对，不能当整题通过。

### 3.2 Graphiti：四轴时间与“显式矛盾才作废”

**来源**

- `graphiti_core/edges.py:228-258` `EntityEdge`
- `graphiti_core/utils/maintenance/edge_operations.py:758-840` `_apply_temporal_invalidation` / `resolve_edge_contradictions`
- `graphiti_core/utils/maintenance/temporal_edge_utils.py:17-71` `normalize_future_temporal_bounds`
- `graphiti_core/prompts/dedupe_edges.py:35-97` 矛盾判定硬规则
- `graphiti_core/prompts/extract_edges.py:24-180` `valid_at` / `invalid_at` 抽取规则
- `graphiti_core/search/search_helpers.py:20-65` `search_results_to_context_string`

**机制**

Graphiti 的事实是边（`EntityEdge`），每条边至少有四个时间：

```python
created_at: datetime          # 系统写入时间
valid_at: datetime | None     # 事实开始为真的时间
invalid_at: datetime | None   # 事实不再为真的时间
expired_at: datetime | None   # 系统把这条边标记为失效的时间
reference_time: datetime | None  # 产生这条边的 episode 时间
```

`_apply_temporal_invalidation()` 的顺序很值得抄：

1. 如果新边自己带了 `invalid_at` 且没有 `expired_at`，说明它一进来就是历史事实，直接 `expired_at = now`。
2. 如果新边没有 `expired_at`，把候选按 `valid_at` 从早到晚排；如果某个候选的 `valid_at` 晚于新边的 `valid_at`，说明候选更新，反而应该把**新边**标成 `invalid_at = candidate.valid_at`、`expired_at = now`。这处理“补录旧事实”的情况。
3. 调 `resolve_edge_contradictions()`：如果旧边在新边生效前就已经失效，跳过；如果两条有效区间不重叠，跳过；只有旧边的 `valid_at` 早于新边、且区间重叠时，才把旧边 `invalid_at = resolved_edge.valid_at`、`expired_at = now`。

这段代码的关键不是“新覆盖旧”，而是**按有效区间判断谁覆盖谁**。补录一条 2020 年的事实，不会把 2025 年的当前值作废；反过来，2025 年的当前值可以把 2020 年的旧值标成失效。

未来计划的时间规则在 `normalize_future_temporal_bounds()`：

- 句子命中 `will / plans to / promises to / scheduled to / going to` 等未来断言时，`valid_at` 取说话时间（`reference_time`），不取未来发生日。
- 未来发生日保留在 `fact` 文本或属性里，不塞进 `valid_at`。
- 软 deadline（`by Friday`、`before Q3`、`due on`）不是 `invalid_at`；只有“持续状态在未来某天结束”（例如“works at Acme until Jan 15”）才允许未来 `invalid_at`。

矛盾判定在 `dedupe_edges.py` 里写得很硬：

```text
NEVER mark facts as contradicted unless the new fact explicitly makes the old fact false.
Do NOT infer contradiction from recency alone, episode dates, meeting dates,
weekly snapshots, section headings such as "updates" or "status changes",
or a new event involving the same entities.
```

它还专门防“角色/所有权被活动误伤”：一个人继续在项目上做事，不等于他不再负责这个项目。这个负例对 CMB 的“真实变化”很重要：很多题是同一实体后续活动，不是身份变更。

检索侧，`search_results_to_context_string()` 不隐藏旧边，而是把每条事实渲染成：

```json
{"fact": "...", "valid_at": "...", "invalid_at": "Present"}
```

块头明确说“事实在 valid_at 和 invalid_at 之间有效；invalid_at 为 Present 表示仍有效”。这把“旧值”变成有区间标注的历史事实，而不是让模型猜。

**量化结果**

仓库内没有 CMB 跑分。代码内可量化的约束是：每条边一次去重/矛盾分类、一次时间抽取（如果未带时间）；`resolve_edge_contradictions` 是 O(candidates)，不是全库比较。Zep 摄取层在 `pipeline.py` 里对缺失 `created_at` 给出明确警告：会用 ingestion time，导致“fact validity timelines and invalidation ordering”被破坏。这是少见的、把时间缺失当成数据质量事故来处理的实现。

**适用条件**

- 事实可以表示成“实体-关系-实体”的三元组。
- 每条事实能拿到一个 `reference_time`（消息时间或文档日期）。
- 可以接受“旧事实留在图里”，由查询时按时间过滤/排序。
- 有 LLM 预算做抽取和矛盾分类。

**失败条件**

- 没有 `valid_at` 的候选不会参与作废比较；`_apply_temporal_invalidation` 里多处要求 `valid_at` 非空。时间抽取失败，整条链就退化成“只追加”。
- 没有 `reference_time`，`_extract_edge_timestamps()` 直接返回，不补时间。
- LLM 如果把“同一实体的新活动”误判成矛盾，旧边会被错误失效；提示词只能降低概率，不能证明。
- 检索默认不按 `invalid_at` 过滤，旧边仍会出现在上下文里；如果下游模型不看区间，仍可能拿旧值当现在。
- `expired_at` 和 `invalid_at` 很容易被调用方混用；一旦混用，就会出现“系统刚写入就过期”或“事实已失效但系统时间未到”的错。

**可借用点**

- 给 `dsh-mnemonic` 的记录补 `validFrom`，并把现有 `validTo` 明确定义为“事实失效时间”；另加 `supersededAt` 或 `recordedAt` 表示“系统何时作废”。现在 `store.js` 的 `validTo = by.eventAt || by.createdAt || Date.now()` 把两者混在一起。
- `resolveCurrent()` 不要只返回记录，返回 `{ rec, validFrom, validTo, hops, reason }`；渲染层才能写 `[as of 2026-10-31]` 或 `[superseded; as of 2026-11-02]`。
- 未来计划/承诺的 `validFrom` 用说话时间，不用未来发生日；软 deadline 不写 `validTo`。这条能直接修“把计划当已发生”和“把 deadline 当失效”。
- 矛盾判据写成“明确终止/替换/接任/互斥当前状态”，不写“后来提到/日期更晚”。这条应该替换 `RECALL_RULES` 第 4 条的模糊表述，而不是新增第 8 条。

**不采用的原因**

- 不把 Graphiti 的 Neo4j 图、边抽取、社区摘要整条链路搬进 `dsh-mnemonic`；迁移成本和延迟都不匹配。
- 不对每条记忆都做一次 LLM 时间抽取；CMB 单轮预算撑不住。只对“带时间词/新旧冲突”的记录做确定性推断或小模型补抽。
- 不采用“检索默认返回旧边让模型自己看区间”作为唯一方案；我们的模型更小，必须在渲染层把当前值前置/标注。

**实测判据**

- 58 道“真实变化”+ 47 道“没解释的矛盾”配对跑：旧值当现在的题净减 ≥10，且新值/旧值同时出现的题不下降。
- 补录/回放场景：构造 20 条“先发生、后补录”的记录，作废方向错误为 0；如果补录旧事实把当前值作废，直接回滚。
- 计划类 20 条：`validFrom` 必须等于说话时间，不能等于未来发生日；错一条记一个。

### 3.3 Letta：块级快照，不是事实级版本

**来源**

- `letta/orm/block.py:20-65` `Block` / `version` / `current_history_entry_id`
- `letta/orm/block_history.py:12-46` `BlockHistory`
- `letta/services/block_manager.py:840-910` `checkpoint_block_async`
- `letta/functions/function_sets/base.py:250-450` `rethink_memory` / `memory_replace` / `memory_insert`
- `letta/orm/passage.py` archival passage 的 `created_at` / 索引

**机制**

Letta 的 core memory 是一块可变文本，按 `label` 分区（`human`、`persona`、`system` 等）。编辑工具是：

- `memory_replace(label, old_string, new_string)`：要求 `old_string` 在块里**逐字出现且唯一**；找不到或多处出现都报错，不猜。
- `memory_insert(label, new_string, insert_line)`：按行插入。
- `rethink_memory(new_memory, target_block_label)`：让模型重写整块，docstring 明确要求“包含所有当前信息，不包含过时或矛盾的信息”。

块级版本不是事实版本：

- `Block.version` 是 SQLAlchemy 乐观锁计数器，每次状态变更 +1，用于并发写冲突。
- `BlockHistory` 是整块快照，字段包括 `value`、`sequence_number`、`actor_type`、`actor_id`；`checkpoint_block_async()` 把当前块复制进历史，并截断 redo 链。
- 没有“事实 ID”“valid_at”“invalid_at”“矛盾分类”。历史只能回答“这个块以前长什么样”，不能回答“这条事实什么时候被谁改成什么”。

archival memory 是另一条线：passage 有 embedding、tags、`created_at`，按 agent 隔离，支持语义检索和时间范围；没有作废链。

**量化结果**

仓库内没有 CMB 跑分。代码内可量化的约束是：`memory_replace` 要求唯一匹配；`BlockHistory` 每次 checkpoint 写一整块；`version` 乐观锁冲突时失败，不自动合并。

**适用条件**

- 记忆是“人设/用户画像/当前任务状态”这种可以整块重写的摘要。
- 写入频率不高，块不大，快照成本可接受。
- 可以接受“模型重写时可能丢细节”，但需要能回滚。

**失败条件**

- `memory_replace` 只做精确字符串匹配；模型一旦改写旧串（多一个空格、换一种说法）就失败。
- `rethink_memory` 是整块重写，模型可以静默删掉它认为“过时”的细节；没有逐条审计。
- 块历史是字节级快照，不是语义级版本；回滚能恢复文本，但不能告诉作答模型“现在哪条事实有效”。
- 多主体场景下，`label` 只是分区名，不是实体 ID；同一块里混着“他/我/别人”时仍会归错。

**可借用点**

- 块级快照 + 乐观锁很适合 `dsh-mnemonic` 的“常驻事实卡/画像卡”：每次重写前 checkpoint，写失败可回滚。
- `rethink_memory` 的“只保留当前、不过时、不矛盾”是一句好的重写指令；但只能用于摘要卡，不能作为事实级当前值机制。
- archival passage 的 `created_at + tags + agent_id` 是一个干净的主体/时间边界；`dsh-mnemonic` 的 `scope` 可以借鉴这种硬隔离。

**不采用的原因**

- 不把“整块重写”作为解决新旧冲突的主方案；它太容易丢证据，也无法解释“为什么这条是现在”。
- 不引入 Letta 的完整 ORM/服务层；我们只需要记录字段和渲染，不需要数据库迁移。

**实测判据**

- 如果给 `dsh-mnemonic` 加事实卡快照：做 30 次连续编辑，检查期望保留的事实是否 ≥90%；低于 90% 回滚。
- 快照恢复测试：随机删一条当前值后恢复，旧值不能重新变成“现在”。

### 3.4 Cognee：最接近“当前值 + 矛盾”的开源实现

**来源**

- `cognee/tasks/memify/review_conflicts/review_entities.py:20-180` 审阅管线
- `cognee/tasks/memify/review_conflicts/select_review_facts.py:58-180` 候选生成
- `cognee/tasks/memify/review_conflicts/accept_review.py:40-170` 响应校验
- `cognee/infrastructure/llm/prompts/review_conflicts.txt` 判定规则
- `cognee/modules/retrieval/utils/conflict_context.py:96-205` 冲突读取/渲染
- `cognee/modules/retrieval/graph_completion_retriever.py:195-235` 冲突块追加
- `cognee/infrastructure/engine/models/DataPoint.py:96-109` `created_at/updated_at/version`

**机制**

Cognee 把冲突审阅放在 `improve()` 的 memify 阶段，不在每轮写入时做。它先做**确定性候选生成**，再让 LLM 判定。这个两段式是重点。

候选生成（`select_review_facts.py`）：

- 对每个 subject（实体），把事实按“值”分组：
  - 普通实体值：如果两个值的类型有交集，归入同一组；
  - 时间值：按同一个 relationship 归组；
  - 语句：两条 statement 如果共享至少 2 个内容词、且各自带不同数字/日期/代码，配成一对。
- 只保留至少 2 个值、且来自至少 2 个不同文档的组（`MIN_GROUP_VALUES=2`、`MIN_GROUP_DOCUMENTS=2`）。
- 这样一个主体最多只比较少量候选，不会把全库两两比较。

LLM 判定（`review_conflicts.txt`）：

- `fixed`：只可能有一个值曾为真，差异说明某个来源错了；所有值都标 `conflicting`。
- `time_varying`：世界可以变，按日期排序；最新值标 `current`，更早的值标 `superseded`；如果值回退，旧值和新值都标 `current`。
- `time_varying` 但没有日期/时间词排序：全部 `conflicting`。
- 计划/提议不算冲突；同一事物的不同说法、不同范围/部分、需要未展示信息才能判断的，都不报。
- “clean handover”也要报：日期能说明哪个值现在成立，但不会消除“曾经有过另一个值”这件事。

`accept_review.py` 做严格校验：

- 标签必须来自本次 prompt 展示过的 fact；未知/重复标签直接拒绝整次响应。
- 冲突事实必须触及 `about` 这个 subject；否则拒绝。
- `_exclude_date_values()` 把“日期”这种元数据从冲突值里排除，避免把 `2024` 和 `2025` 当成两个冲突值。
- `_is_ordering_reversed_by_dates()` 如果 LLM 提议的 `current/superseded` 顺序和来源日期相反，就把所有值改成 `conflicting`，并在 text 里追加“Supplied dates disagree with the proposed ordering”。

写入与读取：

- `FactConflict` 存 `about_id`、`attribute`、`kind`、`status`、`values`、`sources`。
- 每条事实的 `conflict_marks` 记录 `status`、`conflict_id`、`effective_date`、`resolution_source`。
- `fact_status()` 的优先级是 `conflicting > superseded > current`；用户选择的事实优先于自动审阅（`is_user_selected_fact`）。
- `status_label()` 渲染 `[current]`、`[as of 2026-10-31]`、`[superseded; as of 2026-10-31]`。
- 检索时 `attach_chunk_conflicts()` 把冲突文本挂到命中的 chunk 上，`format_conflicts()` 生成 `## Fact conflicts` 块，`resolve_edges_to_text()` 把它追加在证据之后。

另外，`GraphCompletionContextExtensionRetriever` 有 4 轮上下文扩展：用上一轮 completion 作为新查询，合并新三元组，直到不再新增；这是另一种“检索后回读/扩展”。

**量化结果**

仓库内没有 CMB 跑分。代码内可量化的约束很明确：审阅输入预算 8,000 token、每次最多 25 个 subject、最多 4 轮扩展、候选组至少 2 值/2 文档。它们不是效果分，但能直接估算成本。

**适用条件**

- 有实体/关系图，能把事实归到 subject 和 attribute。
- 冲突审阅可以离线/批量跑，不必每轮在线做。
- 能接受“旧事实不删，只打状态标签”。

**失败条件**

- 只在 `improve()` 里跑；如果没调度，库里永远没有冲突节点。
- 候选生成依赖类型/关系/数字；纯自然语言里没有数字、没有类型、没有图结构的冲突会漏。
- LLM 仍可能把“计划/提议”误判成冲突；提示词降低了概率，但没有确定性证明。
- 冲突块只挂在 graph-completion 系列 retriever；如果走 chunks/summaries retriever，可能看不到冲突块。
- `current` 不是删除；如果下游按相似度取回旧事实且不看 `status_label`，旧值仍可能被当现在。

**可借用点**

- 这是最适合 `dsh-mnemonic` 的“最小冲突模型”：`subject + attribute + values + status(current/superseded/conflicting)`，不需要图数据库。
- 先确定性选候选，再 LLM 判定；不要每轮把所有记忆两两比较。
- 状态直接写进证据行：`[as of date]`、`[superseded; as of date]`、`（另有说法，未说明哪个为准）`。
- 用户明确纠错的选择要高于自动审阅；自动审阅不能推翻用户已经确认的当前值。
- 日期顺序和 LLM 提议顺序相反时，标 `conflicting` 而不是硬选一个；这条能直接减少“编日期”。

**不采用的原因**

- 不采用完整 `improve()` 管线、Neo4j 冲突节点、8k token 审阅预算；对单轮聊天太重。
- 不在每轮注入时跑冲突 LLM；只做离线/夜间批量，或只对“显式改口”做确定性处理。
- 不采用“所有冲突都标 conflicting”的保守策略；CMB 需要能答出当前值，全部标冲突会变成过度弃权。

**实测判据**

- 47 道“没解释的矛盾”+ 58 道“真实变化”+ 48 道“纠错”做 150 题分层子集；冲突状态上线后，整题净增 ≥15 才进生产候选。
- 副作用：`conflicting` 标记导致的“该肯定却说不确定”增加 ≤5 题；“旧值当现在”净减 ≥10。
- 如果冲突块让答案长度增加 >25%，先砍冲突文本长度，不砍状态标签。

### 3.5 LangMem：按 id 原地覆盖，默认不删

**来源**

- `src/langmem/knowledge/extraction.py:174-215` `_MEMORY_INSTRUCTIONS`
- `src/langmem/knowledge/extraction.py:217-330` `MemoryManager`
- `src/langmem/knowledge/extraction.py:536-620` `create_memory_manager`
- `src/langmem/knowledge/tools.py:263-340` `create_manage_memory_tool`
- `src/langmem/knowledge/tools.py:391-470` search tool

**机制**

LangMem 用 Trustcall 的 JSON patch 机制管理记忆：

- `existing` 以 `(id, schema, memory)` 形式传入；
- 模型可以 insert 新记忆、update 同 id 的记忆、delete（`RemoveDoc`）；
- 默认 `enable_deletes=False`，所以通常只 insert/update；
- `MemoryManager` 可以多步迭代（`max_steps`），每步把已处理的记忆过滤后继续。

`_MEMORY_INSTRUCTIONS` 要求：

- 关注“偏离现有记忆和预期”的新信息；
- 合并/压缩冗余记忆，按可靠性和新近度加强；
- 删除错误或冗余记忆，保持内部一致；
- 不确定信息带 confidence `p(x)` 和理由。

但这是 prompt 级要求，不是结构化冲突检测。namespace 是 `("memories", "{langgraph_user_id}")`，主体隔离靠 namespace，不靠每条事实的 `subject` 字段。

**量化结果**

仓库内没有 CMB 跑分。代码内可量化的约束：默认不删除；每次最多 `max_steps` 轮；update 复用同一个 id。

**适用条件**

- 记忆是“可覆盖的摘要/偏好”，不是需要保留完整历史的审计记录。
- 用户明确纠错时，希望直接改当前值，而不是追加一条冲突。

**失败条件**

- 原地 update 会覆盖旧值；没有历史就无法回答“我以前叫什么”。
- 删除默认关闭，但 update 仍然会丢旧文本；`enable_deletes=False` 只防物理删除，不防信息丢失。
- 没有事实级时间；store 的 `created_at/updated_at` 是写入时间，不能回答“这件事什么时候是真的”。
- 多轮 patch 可能把同一条记忆反复改写，最后只剩模型认为“重要”的部分。

**可借用点**

- 显式纠错应该按 id 更新同一条记录，而不是新增一条“不是 X，是 Y”的冲突记录；这能减少检索时的重复。
- 更新时保留 `previous`/`history` 字段，渲染时只显示当前值，但旧值仍可查。
- namespace 作为硬主体边界；`dsh-mnemonic` 的 `scope` 是会话级，可以再加 `subject` 做会话内人物隔离。

**不采用的原因**

- 不采用无历史覆盖；CMB 的“纠错”和“以前”题需要旧值。
- 不采用纯 prompt 的“删除错误记忆”；没有结构化判据，模型会把“后来提到”误当“旧值错误”。

**实测判据**

- 48 道“纠错”题：当前值使用率上升，旧值复现率下降；如果旧值复现率不降，说明只改文本不够，需要在渲染层标旧值。
- 20 条“改回旧值”测试：A→B→A 不能形成环；必须能表达“A 现在又是当前值”。

### 3.6 A-MEM：只演化元数据，不解决事实冲突

**来源**

- `agentic_memory/memory_system.py:24-82` `MemoryNote`
- `agentic_memory/memory_system.py:127-158` 演化提示词
- `agentic_memory/memory_system.py:590-710` `process_memory`
- `agentic_memory/memory_system.py:315-344` `find_related_memories_raw`

**机制**

A-MEM 的笔记有 `content`、`keywords`、`tags`、`links`、`timestamp`、`context`、`evolution_history`。新增笔记时：

1. LLM 抽 keywords/context/tags；
2. 用向量找 top 5 邻居；
3. LLM 决定 `should_evolve`，动作是 `strengthen`（加链接/改自己的 tags）或 `update_neighbor`（改邻居的 context/tags）；
4. 只改元数据，不改 `content`；
5. 检索时把 linked neighbors 一并拼进结果。

**量化结果**

仓库内没有 CMB 跑分；A-MEM 论文的 LoCoMo 数字不在这个快照的可复现脚本里。代码内可量化的约束：top 5 邻居、每次新增一次演化 LLM 调用、邻居扩展最多 k 条。

**适用条件**

- 记忆是“主题/概念”型，链接和标签比事实当前值更重要。
- 可以接受元数据随新笔记演化。

**失败条件**

- 不改正文，所以“旧值/新值”冲突仍然存在。
- `update_neighbor` 会让旧笔记的 context/tags 被新笔记改写，可能造成主题漂移。
- 代码里邻居索引用的是列表下标，和 `self.memories` 的 dict 顺序耦合；这是实现脆弱点，不适合直接搬。
- 没有主体字段；多人场景会把不同人的事实链在一起。

**可借用点**

- `links` + 邻居扩展可以用于“同一事件的多条证据”，但不要默认打开；Whale 的实测是负收益。
- `evolution_history` 字段的思路可以借：每次 supersede/merge 写一条审计记录，渲染时不显示，排查时用。

**不采用的原因**

- 不用 A-MEM 的“每次新增都演化邻居”作为主链路；成本高、漂移大，且不解决当前值。
- 不用它的邻居扩展作为默认检索；CMB 里多跳不是主要矛盾。

**实测判据**

- 如果做链接扩展，先测 30 道多跳/关联题；没有净增就不上线。
- 元数据演化必须配“主题漂移”检查：随机抽 50 条被 update 的邻居，人工看 context 是否仍成立；错误率 >10% 回滚。

### 3.7 dsh-neo4j-memory：把“命中”变成“可回读的原文范围”

**来源**

- `src/retrieval.ts:4` `RETRIEVAL`
- `src/store.ts:392-420` `rankEvidence`：summary 向量 + source 向量 + 可选 BM25
- `src/evidence.ts:2` `EVIDENCE_LIMITS`
- `src/evidence.ts:118-179` `buildEvidence` / `renderMemoryEvidence`
- `index.js:112-130` 工具描述

**机制**

Neo4j 项目不是“把 40 条正文全倒给模型”，而是三层：

1. **8 条展开证据**：每条有 `id`、`summary`、`chapter/title/session`、`quote.range/text`、`read.start/limit/total`、`via`、`time`。
2. **24 条一行候选索引**：只有 id、章节、session、摘要前 100 字；模型可以按 id `read`。
3. **回读命令**：`read event_id=<id> limit=<total>` 读整条；`read event_id=<id> start=... limit=...` 分段；`expand concept_id=<id>` 沿概念扩展；`nearby event_id=<id>` 补同章/同会话邻居。

块头不是“请根据记忆回答”，而是声明边界：

```text
摘要待核；原文范围[起点:终点)按Unicode字符计。
共享概念及来源邻近不代表因果或发生顺序。
```

`renderMemoryEvidence()` 还明确写“只交付相关片段，不代表全文完整覆盖；可换问题检索同一事件或按位置补读”。这直接防止模型把“本次没给”当成“全文没有”。

检索是三路 RRF：`RETRIEVAL = { candidates: 40, rrfK: 60, keywordBonus: .10, mmrLambda: .75 }`。summary 向量和 source 向量各 40 条，BM25 可选；`rerankEvents()` 做 RRF、关键词覆盖加成、MMR 去冗余。`sessionDiverse()` 限制同一 session 占比，避免一个长会话挤掉其他证据。

**量化结果**

前置调研记录：榜单 `684/714`，作者自测 + 28 题抽查；不是独立复现。本文只把它当机制线索。代码内可量化：8 条展开、24 条候选、每路 40、RRF k=60、MMR λ=.75、cursor 15 分钟。

**适用条件**

- 宿主支持多轮工具调用，模型愿意/会调用 `read/expand/nearby`。
- 原文可寻址（有 event/source/chunk ID 和字符范围）。
- 能接受 Neo4j 依赖和工具延迟。

**失败条件**

- 模型不调用 `read`，就只看到 8 条摘要 + 24 条索引；细节题仍会错。
- `time_hint` 是“存储日期”硬过滤，工具描述明确说“不一定是事发日”；拿它当事实发生日会错。
- `shared concepts` 只是共享概念，不代表因果/顺序；块头已经警告，但弱模型仍可能编因果。
- 多轮工具调用增加延迟和失败面；一次失败不代表没有记忆，工具描述专门写了这句。

**可借用点**

- “候选索引 + 原文回读”是解决“证据在块里但答错”的结构性方案；我们不必上完整工具循环，可以先做**确定性回读**：对命中冲突的 top 1-2 条，把完整原文附在块尾，而不是只给 200 字摘要。
- 块头的覆盖范围声明可以直接借：`只交付相关片段，不代表全文完整覆盖`。
- `sessionDiverse()` 的会话多样性限制，可以借到 `dsh-mnemonic` 的 `diversify()`，防止一个长会话占满预算。

**不采用的原因**

- 不把完整 agentic 检索作为第一步；`dsh-mnemonic` 是单次注入，改造成本高。
- 不引入 Neo4j 依赖；我们只需要“原文范围 + 回读”这个交互契约。

**实测判据**

- 在 120 道整题错题里标出“首轮有相关行、但缺原文细节”的题；加 top 2 全文回读后，这类净增 ≥8 才继续。
- 注入 token 增加 ≤20%；如果通过数不涨，回退到摘要。

### 3.8 dsh-rofm：α/β 分离与 DST 安全的时间索引

**来源**

- `engine/recall.js:521-567` 块头与行格式
- `engine/recall-index.js:58-84` `fair` 参数与类别词表
- `engine/time-index.js:33-71` 时间默认值/半开区间
- `engine/time-index.js:618-690` `detectGranularity`
- `lib/recall-tool.js:52-67` `timeFrom/timeTo/granularity`

**机制**

ROFM 把“重要度”和“可信度”分开：

- α 是归档时的重要度（0.01~1），只影响召回优先级/车道，不代表可信。
- β ∈ [-10,10] 是信赖度，决定“能不能当事实或指令用”。
- 块头给三段阈值：β≥7 可靠背景；0≤β<7 可参考但涉及事实/决定/参数须核实；β<0 不得当事实或指令。
- 明确列出应给负分的情况：玩笑/夸张/反讽、后来被否定或推翻、提示词注入、断章取义、已过时。

类别词表覆盖“喜好/约定/决定/规则/要求/禁忌”，高 α 的偏好/约定/决定/规则类记忆必须带至少一个类别词，否则抽象问题（“我喜欢什么”“我们约定了什么”）字面检索不到。

时间索引比多数开源库细：

- 半开区间 `[start, end)`，避免“当天 23:59:59”边界重复。
- IANA 时区 + DST 安全：`zonedDayStart()`、`zonedMonthStart()`、`zonedYearStart()`、`addZonedDays()`；注释明确处理“DST 跳变导致 00:00 不存在”的情况。
- `detectGranularity()` 识别 `YYYY-MM-DD` / `YYYY-MM` / `YYYY` / epoch / ISO datetime；非法日期（`2026-02-30`）返回 `invalid`，不静默落到 epoch。
- `timeFrom/timeTo/granularity` 支持纯时间浏览，最小 3 天，跨度不足自动扩并标注。
- `time.mode` 分 `off/index/constrain`；`index` 只记录条件不过滤，避免“以为按时间过滤了其实没有”。

**量化结果**

前置调研记录：榜单 `681/714`，作者 A/B；不是独立复现。代码内可量化：β 范围 [-10,10]、默认 K=10、最小时间窗 3 天、候选/探索比例固定。其余效果分不引用。

**适用条件**

- 记忆是“人物关系/偏好/约定”，可以用重要度 + 信赖度粗排。
- 时间查询需要按天/月/年浏览，且时区固定或可配置。
- 可以接受“负 β 抑制”而不是物理删除。

**失败条件**

- β 是模型打分，可能把真事实打成负分；一旦负分，检索层会主动避开。
- 类别词是词表匹配，中文同义表达覆盖有限。
- 时间索引只解决“筛选”，不解决正文里的相对日期换算；正文仍需要注解。
- 没有事实级作废链；“后来被推翻”只体现为 β 降低，旧值仍可被召回。

**可借用点**

- 时间索引的 DST/粒度代码可以直接作为 `dsh-mnemonic lib/text.js extractTimeWindow()` 的参考；当前 `extractTimeWindow()` 只有日/周，缺月/年/区间。
- β 的三档阈值可以简化成 `trust: reliable/verify/do-not-use`，不要引入完整数值评分器。
- 类别词表可以补 `dsh-mnemonic` 的抽象偏好/约定召回。

**不采用的原因**

- 不引入完整 α/β 轮转引擎；成本和维护面太大。
- 不用模型每轮给 β 打分；只对显式否定/嘲讽/纠正做规则降级，避免误杀。

**实测判据**

- 43 道“时间约定”+ 44 道“相对日期”：补月/年/区间后，日期类净增 ≥6；非时间题不下降。
- 20 条 DST 边界样本（America/New_York 的 23/25 小时日）：日期窗口错误为 0。

### 3.9 dsh-dot：相对日期注解的“引用/转述保护”

**来源**

- `src/memory/memory.js:60-72` 检索参数
- `src/memory/recall.js:353-370` `renderTurns`
- `src/memory/recall.js:464-535` `query`
- `src/memory/when.js:21-72` `dayHeading` / `annotate`
- `src/prompts/memory.recall.header.txt`
- `bench/chat-memory-benchmark.mjs:288-291`

**机制**

Dot 的检索是向量 20 + BM25 20 → cross-encoder rerank → top 10；没有 reranker 时用 `contrastCut` + interleave，且**不补足**：相关不够就少于 10 条，不拿弱相关填预算。

渲染按日期分组，每天标题是 `06-22 周一 · 15 天前`；相对日期由 `when.js` 就地补：

```text
明天（=06-23）
```

`annotate()` 的保护很关键：

- 只换算无歧义表达：今天/明天/后天/大后天/昨天/前天/大前天、这周X/下周X/上周X；不换算“月底”“X 号”“周末”“裸周三”。
- 扫描引号范围，引号内的内容不换算。
- 跳过转述/假设句：`说|讲|听说|据说|告诉我|问我|写着|提到|以为|如果|假如|要是|万一|假设|梦到|梦见|的话`。
- 已经写了日期的（`明天（06-23）`、`明天 6 月 23 号`）不重复补。

这解决的是“他说他昨天去了”这种句子：如果把“昨天”按当前说话时间换算，就会把别人的昨天算错。`dsh-mnemonic` 的 `lib/dates.js resolveRelativeDates()` 目前没有这层引用/转述保护，是一个具体缺口。

作答侧只有一句：

```text
只依据你记得的事和聊天内容回答；记不清、没有依据的就照实说不确定，不要编。
```

**量化结果**

前置调研记录：榜单 `654/714`，作者自测；`docs/DESIGN.md` 记录 0.19 加 BM25/人名/取代/日历只从 621→622，0.20 改“原话负责证据，三栏笔记负责长期状态”到 654。这些是作者自报，不是独立复现。代码内可量化：候选 20+20、top 10、1,500 token、rerank 模型 279MB（base）/571MB（v2-m3）。

**适用条件**

- 有原话和消息时间；不需要抽取式事实。
- 可以接受 reranker 的模型体积/延迟，或接受无 reranker 的 contrast 回退。
- 日期表达主要是中文口语。

**失败条件**

- 正则覆盖有限；不常见表达（“隔天”“转天”“大下周”）会漏。
- 引号/转述保护是启发式，可能漏掉没有引号的间接引语。
- 没有事实级版本；新旧值仍靠原话和 rerank。
- reranker 模型 279–571MB，对低配宿主不友好。

**可借用点**

- `when.js annotate()` 的引用/转述保护是最值得直接抄的小代码；可以移植到 `dsh-mnemonic lib/dates.js resolveRelativeDates()` 或 `inlineDateHints()`。
- “不补足”策略可以借到 `dsh-mnemonic` 的 `diversify()`：相关度不够时宁可少给，不要用弱证据填满预算。
- 日期分组 + `N 天前` 标题可以借到 `renderRecallBlock()` 的块头/分组。

**不采用的原因**

- 不引入 cross-encoder 模型；我们的宿主没有稳定本地 reranker，云 rerank 增加延迟。
- 不采用“原话完全替代事实卡”；CMB 需要当前值/主体/状态，原话本身不够。

**实测判据**

- 44 道“相对日期”+ 43 道“共同编的故事”：加引用/转述保护后，错误日期注解数下降 ≥30%，正确注解不下降 >5%。
- 用 50 条含“他说/如果/梦到/引号”的构造样本，检查不换算率 100%；错一条记一个。

### 3.10 dsh-memu-memory：字段纪律比“高分 prompt”更有用

**来源**

- `lib/inject.js:242-330` `uncertaintyTag` / `accuracyTag` / `dateTag` / `privateHead`
- `lib/inject.js:975-1000` 块头
- `lib/memory.js:48-60` RRF/MMR 参数
- `lib/memory.js:798-900` `hybridCandidateLimit` / `fuseRecallCandidates`
- `lib/memory.js:1140` `mmrSelect`

**机制**

Memu 的 title card 字段顺序是：

```text
- [id] source=user_said · [关于他] 标题 · long_term · date=2026-10-31
  · 12天前 · open_loop · confidence 0.8 · 记忆模糊（...） · 对方不问就别主动提
```

关键字段：

- `source`：`user_said` / `assistant_said` / `imagined` / `inferred`；块头明确“推测、转述与想象不得当成用户原话”。
- `owner`：只有 `about_user` 加 `[关于他]` 前缀；`me/us/about_project` 由块语境隐含。
- `date` vs `anniversary`：一次性日期和每年重复的日期分开。
- `age`：`12天前`，让模型知道“这条还新不新”。
- `open_loop`：未完成事项。
- `confidence` / `uncertainty`：低于阈值时加“记忆模糊，可能记错，别当事实讲”。
- `accuracy`：和 `confidence` 分开；`accuracy` 低但 `confidence` 高时加“记得清楚，但细节未必准”。
- `disclosure`：`only_if_asked` / `never_say`，是语气，不是过滤。

检索是词法 + 向量 RRF，`k=60`，候选 `clamp(topK*4, 12, 40)`，MMR λ=.72。

**量化结果**

前置调研记录：榜单 `653/714`，作者自测；不是独立复现。代码内可量化：RRF k=60、候选 12–40、MMR λ=.72。

**适用条件**

- 记忆条目有稳定 title，且可以用 id/标题回查正文。
- 宿主支持 `memu_private_recall` 这种抽屉工具。

**失败条件**

- 只有 title card，没有正文，模型可能“知道有这条但答不出细节”；必须有回查工具。
- `confidence/accuracy` 是模型/启发式赋值，可能不准。
- `source` 可能标错；标错比不标更危险，因为块头会让模型相信“imagined 不是事实”。
- 没有事实级作废链；新旧值仍靠 source/date/age 推理。

**可借用点**

- 字段顺序和共享 `privateHead()` 防漂移：卡片和全文渲染必须用同一个 head builder。这个工程做法值得直接抄。
- `owner` + `source` + `date` + `age` 四件套，可以补 `dsh-mnemonic` 的“谁说的/什么时候/现在还新不新”。
- `accuracy` 和 `confidence` 分开，能避免“记得清楚=记得准”的混淆。

**不采用的原因**

- 不采用 title-card-only 注入；`dsh-mnemonic` 没有抽屉工具，正文必须一起给。
- 不采用完整 Memu 库/索引；只借字段和渲染纪律。

**实测判据**

- 167 道“未知当事实”+ 36 道“漏必答点”：加 owner/source 后，错误归属净减 ≥8；答案长度增加 ≤15%。
- 如果 `confidence` 标签导致“该肯定却说不确定”增加 >5 题，先去掉 confidence 文案，只留 source/date。

## 4. 跨实现归纳：真正有用的六件事

### 4.1 版本链要保留旧值，不要物理删

五个实现的态度：

- Mem0：只追加 + 链接；
- Graphiti：旧边写 `invalid_at`，不删；
- Cognee：旧事实标 `superseded`，不删；
- Letta：块快照，可回滚；
- LangMem：原地覆盖（反例）。

CMB 的“纠错”和“我以前叫什么”都需要旧值可查。正确做法不是“删旧”，而是“旧值保留、标失效、当前值前置”。

### 4.2 当前值不是“最新写入”，而是“在参考时间有效的值”

Graphiti 的 `resolve_edge_contradictions()` 用 `valid_at` 比较，不是用 `created_at`。补录一条旧事实不会作废当前值；反过来，当前值可以作废旧值。

`dsh-mnemonic` 的 `supersede()` 现在用 `by.eventAt || by.createdAt || Date.now()` 写 `validTo`，需要拆成“事实失效时间”和“系统作废时间”，否则补录/回放会错。

### 4.3 矛盾检测要先缩小候选，再让 LLM 判

Cognee 的候选生成是本文最值得抄的结构：

- 同 subject；
- 同 attribute/类型；
- 至少 2 个值；
- 至少 2 个来源文档；
- 语句对要有不同数字/日期/代码，且共享至少 2 个内容词。

这样 LLM 只看少量真正可能冲突的组，不会把“同一实体的两个不同事件”误判成矛盾。Graphiti 的 `dedupe_edges.py` 则用硬规则防“recency 推断矛盾”。两者可以叠加。

### 4.4 主体归属要在数据层，不要在 prompt 里补

- Graphiti：每条事实是三元组，subject 是实体；
- Cognee：冲突必须 `about` 一个 subject；
- Memu：`owner=about_user`；
- LangMem：namespace；
- Letta：block label + agent_id；
- Mem0：`attributed_to` + user/agent/run 过滤。

`dsh-mnemonic` 只有 `scope`（会话）和 `asstOnly`（助手半句），没有 person/entity 字段。CMB 的第三方事实、助手旧话、共同故事，很多是主体错，不是检索错。

### 4.5 时间归一化要分“说话时间/事发时间/失效时间”

- Mem0：`Observation Date` 是唯一相对时间锚；
- Graphiti：`reference_time` / `valid_at` / `invalid_at` / `expired_at`；
- ROFM：半开区间 + DST + 粒度；
- Dot：引用/转述保护的就地注解；
- Zep：缺失 `created_at` 会破坏 validity timeline，必须报警。

`dsh-mnemonic` 已有 `spokenAt` / `eventAt`，这是好基础；缺的是 `validFrom`、月/年/区间时间窗、以及引用/转述保护。

### 4.6 grounding 是结构，不是更多“不要编”

- Graphiti：区间 + “Present 表示仍有效”；
- Cognee：`[as of date]` / `[superseded]` / `## Fact conflicts`；
- Memu：source/confidence/accuracy/uncertainty；
- ROFM：β 阈值；
- Neo4j：覆盖范围声明 + 原文范围；
- Dot：一句式“只依据记得的事”。

这些都不是“再写一条不要编”，而是让模型在每行证据上看到“这条能不能当事实、是什么时候的、谁说的、有没有旧说法”。

## 5. 对 `dsh-mnemonic` 的具体落点

以下只写最小改动，不改生产代码；按优先级排序。

### 5.1 P0：旧值命中但当前值不在块里时，补当前值

**现状**

`lib/card.js` 的 `renderRecallBlock()` 已经做了两件好事：

- `renderCard()` 过滤 `supersededBy`，旧值不会挂在常驻卡上；
- 同块新旧一起出现时，块尾 `nowLine` 补“（现在：…）”。

但 `nowLine` 只从 `list`（当前召回块）里取当前值：

```js
const nowLine = replacedIds.size
  ? `（现在：${list
    .filter((h) => replacedIds.has(h.rec.id) && !h.rec.supersededBy)
    ...
```

如果旧值被召回、当前值没被召回，`successorInBlock` 为 false，行内只写“（以前的说法，现在已经不是这样了）”，块尾没有当前值。模型知道“不是这个”，但不知道“那现在是什么”。

**最小改动**

- 文件：`lib/card.js`
- 函数：`renderRecallBlock()`
- 行为：当 `hit.rec.supersededBy` 存在且 `currentOf(hit.rec)` 返回当前记录时，不管当前记录是否在 `list`，都用 `byId` 取它的 `userPartOf(text)`，在 `nowLine` 里补一条“（现在：…）”；预算不够时优先保留这一条，砍后面的弱证据。

**预期行为**

旧值被命中时，块尾一定有一个当前值；模型不需要靠“现在已经不是这样了”自己猜。

**验证**

构造 30 条“旧值命中、当前值不在 top K”的样本；当前值出现率从 0 到 100%；整题通过数净增 ≥5 才继续。

### 5.2 P0：把 `validTo` 拆成事实失效时间和系统作废时间

**现状**

`lib/store.js` 的 `supersede()`：

```js
old.supersededBy = by.id
if (!old.validTo) old.validTo = by.eventAt || by.createdAt || Date.now()
old.basis = 'tool'
```

`validTo` 同时承担“事实何时失效”和“系统何时作废”。补录/回放时会错。

**最小改动**

- 文件：`lib/store.js`
- 函数：`MemoryStore.add()` / `supersede()`
- 字段：
  - `validFrom = eventAt || spokenAt || createdAt`（事实开始为真）
  - `validTo = by.eventAt || by.spokenAt || null`（事实失效；不知道就不写）
  - `supersededAt = Date.now()`（系统何时处理）
  - `supersededBy` 保留
- 文件：`lib/supersede.js`
- 函数：`resolveCurrent()` 增加返回 `validFrom/validTo/supersededAt`，或新增 `resolveCurrentState()`，不改变现有 `resolveCurrent()` 调用方。

**预期行为**

补录 2020 年的事实不会把 2025 年的当前值标成过期；渲染层可以写 `[as of 2026-10-31]`，而不是只写“以前”。

**验证**

20 条“先发生、后补录”样本，作废方向错误为 0；20 条“当前值被补录旧值覆盖”样本，当前值保留率 100%。

### 5.3 P1：给记录加 `subject`，渲染时标“他/我/别人/助手”

**现状**

`lib/store.js add()` 只有 `scope`；`lib/card.js` 只有 `asstOnly` 标“她说的”。多人对话/第三方事实没有主体字段。

**最小改动**

- 文件：`lib/store.js`
- 函数：`add({ ..., subject = '' })`
- 字段：`subject: 'user' | 'assistant' | 'third' | ''`，默认从 `source.kind` 推断；工具显式写入可覆盖。
- 文件：`lib/card.js`
- 函数：`renderBody()` 或 `renderRecallBlock()` 的行前缀
- 行为：`subject === 'third'` 时行首加 `〔别人说的〕`；`subject === 'assistant'` 时沿用 `〔她说的〕`；`subject === 'user'` 不额外标，避免每行都占字。

**预期行为**

第三方事实和助手旧话不会被当成用户当前设定；CMB 的“共同编的故事”和“助手旧话”两类错误下降。

**验证**

167 道“未知当事实”+ 43 道“共同编的故事”：错误归属净减 ≥8；答案长度增加 ≤10%。

### 5.4 P1：把 `profile.js` 的稳定槽位复用到冲突分组

**现状**

`lib/profile.js` 已有 `stableAttrOf(rec)` 和 `HARD_RULES`，只允许“我叫/我住在/我换工作/我每天…”这类定义式陈述覆盖旧值；临时状态（“今天上班好累”）不会覆盖。这是一个现成的、确定性的 subject/attribute 提取器。

**最小改动**

- 文件：`lib/profile.js`
- 函数：`stableAttrOf(rec)` 保持不动；新增导出 `stableAttrSlot(rec)` 或在 `card.js` 里复用 `stableAttrOf`。
- 文件：`lib/supersede.js` 或新 `lib/conflicts.js`
- 函数：`groupBySubjectAttribute(records)`：按 `scope + subject + stableAttrOf(rec)` 分组；同组 ≥2 条且值不同，标 `conflicting`。
- 文件：`lib/card.js`
- 函数：`renderRecallBlock()`
- 行为：同组冲突且没有 `supersededBy` 时，在块尾加一行“（另有说法：…；没有说明哪个为准）”，不要硬选一个。

**预期行为**

“没解释的矛盾”不再被静默合并；模型能看到两个值并知道没有裁决。

**验证**

47 道“没解释的矛盾”：净增 ≥8；如果“该肯定却说不确定”增加 >5 题，缩小冲突组范围，只对 `stableAttrOf` 命中的槽位生效。

### 5.5 P1：时间题单独路由 + 月/年/区间

**现状**

`index.js` 的预算只分 `multiNeed` / `wantsRecall` / 默认三档；没有“时间题”单独路由。`lib/text.js extractTimeWindow()` 只有日/周，缺月/年/区间和 DST。

**最小改动**

- 文件：`index.js`
- 位置：`const budget = multiNeed ? ... : wantsRecall ? ... : ...` 之前
- 行为：加 `timeNeed = /什么时候|哪天|几号|上周|昨天|前天|多久|隔了|几个月|几年/.test(qTrim)`；命中时：
  - `limit = Math.min(cfg.limit, 8)`
  - `inject = Math.min(cfg.injectChars, 600)`
  - `renderRecallBlock` 传入 `sortBy: 'eventAt'`，按时间升序
- 文件：`lib/text.js`
- 函数：`extractTimeWindow()`
- 行为：补 `YYYY-MM` / `YYYY` / `A..B` 区间；半开区间；非法日期返回 null，不静默落到今天。

**预期行为**

时间题不再和普通题共用大池子；日期题证据更集中，模型少被无关旧事干扰。

**验证**

48 道“时间题”+ 44 道“相对日期”+ 43 道“时间约定”：三类合计净增 ≥6；非时间题不下降。

### 5.6 P2：给相对日期注解加引用/转述保护

**现状**

`lib/dates.js resolveRelativeDates()` 只做词面匹配，没有跳过引号/转述/假设。`inlineDateHints()` 会直接给“昨天/下周”补日期。

**最小改动**

- 文件：`lib/dates.js`
- 函数：`resolveRelativeDates()` 或 `inlineDateHints()`
- 行为：移植 Dot `when.js:51-72` 的两层保护：
  1. 扫描成对引号（`“”`、`「」`、`『』`、`""`、`''`），引号内不换算；
  2. 命中词所在小句含 `说|讲|听说|据说|告诉我|问我|写着|提到|以为|如果|假如|要是|万一|假设|梦到|梦见|的话` 时不换算。

**预期行为**

“他说他昨天去了”“如果你明天来”不会被按当前说话时间硬算；日期注解错误下降。

**验证**

50 条构造样本（引号/转述/假设/梦）不换算率 100%；44 道相对日期题正确注解不下降 >5%。

### 5.7 P2：只替换 `RECALL_RULES` 第 4 条，不新增第 8 条

**现状**

`lib/card.js:256` 的 `RECALL_RULES` 第 4 条是：

```text
4. 称呼、关系、住址被改过就用最后一次的；别的事前后说法不一样又没说清，就两个都说，讲一句自己记不太准。
```

这条把“最后一次”当成通用规则，容易把“后来提到同一件事”误当“改口”。

**最小改动**

- 文件：`lib/card.js`
- 常量：`RECALL_RULES`
- 行为：替换第 4 条为：

```text
4. 只有明确改口、终止、接任、搬走这类说法才算旧值作废；只是后来又提到同一件事，不算改口。
   旧值和新值都在时，先用标着“现在”的那条；没有标“现在”就两个都说，讲一句自己分不清哪个是现在。
```

不要新增第 8 条；FollowBench 的证据是约束越多越容易崩，PMem 的全量 -57 也说明叠加“记不清”话术会反噬。

**预期行为**

减少“后来提到=改口”的误作废；同时保留“没有裁决就说两个”的诚实。

**验证**

58 道“真实变化”：旧值误作废净减 ≥5；47 道“没解释的矛盾”：不下降；如果总通过数 -5 以上，回滚这条措辞。

## 7. 明确不采用

| 方案 | 不采用原因 |
| --- | --- |
| 把 Graphiti/Neo4j 整条图链路搬进 `dsh-mnemonic` | 依赖重、迁移大、单轮注入架构不匹配；我们只需要时间字段和作废判据 |
| 每轮跑 Cognee 式 8k token 冲突审阅 | 成本/延迟不可接受；冲突审阅应离线/夜间或只对显式改口做确定性处理 |
| Mem0 旧版 DELETE 矛盾事实 | 旧值不可查，违背“纠错/以前”的需求 |
| Mem0 当前只追加、不判当前值 | 旧值会一直被当现在；必须有渲染层当前值 |
| LangMem 无历史原地覆盖 | 丢旧值，无法回答“以前叫什么” |
| Letta 整块重写作为主方案 | 丢细节、不可审计；只能用于摘要卡 |
| A-MEM 每次新增演化邻居 | 成本高、主题漂移，且不解决事实冲突 |

| 继续堆 `RECALL_RULES` 条数 | PMem 全量 -57 的红线；约束越多越容易崩，应该替换而不是新增 |
| 把“最新写入”当“当前值” | 补录/回放会错；必须用 `valid_at` 比较，不是 `created_at` |
| 把“日期更晚”当“矛盾” | Graphiti/Cognee 都明确禁止；会把同一实体的后续活动误判成改口 |
| 只在 prompt 里写“注意新旧” | 没有结构约束；167 道“未知当事实”已经证明再加一句“不要编”边际收益接近零 |

## 8. 三条最值得抄的代码思路（给最终回复用）

1. **Graphiti 的四轴时间 + 显式矛盾才作废**：`valid_at` / `invalid_at` / `expired_at` / `created_at` 分开；`resolve_edge_contradictions()` 按有效区间判断谁覆盖谁；`normalize_future_temporal_bounds()` 让计划/承诺锚定说话时间，软 deadline 不算失效。落到 `dsh-mnemonic` 是 `store.js` 拆 `validFrom/validTo/supersededAt`，`supersede.js` 返回有效期。
2. **Cognee 的 subject + attribute 三态冲突模型**：先确定性选候选（同主体、同属性/类型、≥2 值、≥2 文档），再 LLM 标 `current/superseded/conflicting`；日期顺序和 LLM 顺序相反时标 `conflicting`；检索时追加 `## Fact conflicts` 和 `[as of date]`。落到 `dsh-mnemonic` 是复用 `profile.js stableAttrOf()` 做分组，`card.js` 渲染“现在的说法/另有说法”。
3. **Neo4j 的“候选索引 + 原文回读 + 覆盖范围声明”**：8 条展开证据 + 24 条一行候选 + `read/expand/nearby`；块头明确“摘要待核、只交付片段、不代表全文覆盖”。落到 `dsh-mnemonic` 是先做确定性回读：冲突命中的 top 1–2 条附全文，不必上完整工具循环。

如果只能先抄一条小代码，先抄 **Dot `when.js annotate()` 的引用/转述保护**：它最便宜，直接减少相对日期误算，且不改变现有架构。
