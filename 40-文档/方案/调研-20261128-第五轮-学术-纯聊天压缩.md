# 纯聊天历史压缩：学术与生产机制调研（第五轮）

日期：2026-11-28  
范围：只做调研，不改代码、不部署。  
目标：给 QQ 聊天 bot 的“纯聊天尾巴摘要/折叠”找可落地的机制证据，而不是找一篇论文照抄。

---

## 0. 结论先行

1. **纯聊天尾巴不要做“整段历史摘要替换”**。生产系统和论文都指向同一个结构：**关闭的旧段做增量摘要，最近若干轮原样保留，原始消息永远可回查**。Anthropic 的 keep-tail、OpenAI compaction 的 retained items、MemGPT 的 recall storage 是同一思路的三种实现。
2. **摘要只做导航，原话才是证据**。MemoRAG 用全局记忆生成线索再去检索原文，平均分 40.2，高于全量上下文 35.0、普通 RAG 29.7；SeCom 直接绕过摘要、返回 segment 原文，在 LoCoMo 上优于 turn/session/summary 三类记忆；MemGPT 给基线只喂“五轮会话的损失性摘要”时 DMR 只有 32.1%，允许搜索完整日志后到 92.5%。
3. **事实漂移不是理论风险，是已经量化的失败模式**。CIKM 2026 的 Compaction Cliff 在 20 个生产 agent 配置上测到：Claude Code 的 `/compact` prompt 一轮后只保留 53% 的安全规则，五轮后 10%。对话摘要本身也差：EMNLP 2022 测到 >35% 的生成摘要与源对话事实不一致；TOFUEVAL 的 summary-level 不一致率在 MediaSum 上是主话题 37.2%、边缘话题 46.0%（MeetingBank 为 30.4%/43.6%），其中 48.5% 的错误是“加入外部信息”。
4. **最值得抄的三条**：① keep-tail + 关闭段增量摘要，永不重写整本摘要；② 段摘要/事实卡做索引，命中后回取原话片段；③ 身份、偏好、承诺、边界、日期这类“不可改写事实”走独立账本，每轮压缩后做事实探针校验。
5. **不要用 provider 的 opaque compaction 存人格事实**。OpenAI 的 compaction item 是加密、不可解释的；Anthropic 的 summary 可读但没有内置事实校验。对 QQ bot 来说，这两者都无法回答“这句话是从哪条消息来的”。

---

## 1. 问题与证据分级

### 1.1 现状判断

宿主每轮把完整会话历史送上游；现有压缩插件只识别“带工具调用的段”，纯聊天尾巴没有工具调用作为切段锚点，所以 `no-candidates`。这不是摘要模型不行，而是**候选生成器的边界定义不覆盖 chat-only 段**。

因此新层要解决的不是“摘要质量”一个问题，而是四个：

- 怎么切出“已经结束的聊天段”，而不切断正在进行的话题；
- 切完以后保留什么、丢什么；
- 摘要如何不把推测写成事实；
- 摘要之后如何证明关键事实还在。

### 1.2 证据分级

本文对每条来源标一个级别，避免把博客和论文混在一起：

| 级别 | 含义 |
|---|---|
| **A** | 同行评审 + 公开代码/数据，结论可复现 |
| **A-** | 顶会/期刊但代码或数据只部分公开，或预印本但有完整 artifact |
| **B** | 同行评审或正式预印本，但没有可复现代码/数据 |
| **C** | 厂商官方文档/工程博客，属于作者自测或生产经验，不是对照实验 |
| **D** | 社区帖子、教程、二手总结，只当线索，不当结论 |

## 2. 生产系统：官方文档怎么说

### 2.1 Anthropic：threshold compaction

- **来源**：Anthropic Docs, *Compaction at a token threshold*, 2026 — https://platform.claude.com/docs/en/build-with-claude/compaction-threshold
- **证据级别**：C（官方产品文档，无公开对照实验）
- **机制**：输入 token 达到阈值触发，默认 150,000，最低 50,000；API 生成一个 `<summary>` 块，后续请求自动丢弃该块之前的所有内容，从摘要继续。摘要 prompt 默认要求写“state, next steps, learnings”；自定义 `instructions` 会**完全替换**默认 prompt，不是追加。`pause_after_compaction` 可以在摘要生成后暂停，让调用方检查或插入保留消息。
- **可借用**：阈值触发 + 可暂停检查 + 摘要块作为显式边界。对 QQ bot 来说，`pause_after_compaction` 等价于“摘要写完先跑事实探针，再决定是否替换”。
- **不采用/限制**：它是整段替换，默认不保留最近原话；摘要 prompt 面向任务 agent，不覆盖“人格/关系/情绪”这类聊天状态；没有内置事实校验。
- **我们的判据**：摘要块必须带 `msg_id` 范围和事实列表；替换前 must-keep fact recall ≥98%，否则不替换。

### 2.2 Anthropic：keep-tail compaction

- **来源**：Anthropic Docs, *Compaction that keeps recent turns*, 2026 — https://platform.claude.com/docs/en/build-with-claude/compaction-keep-recent-turns
- **证据级别**：C
- **机制**：调用方自己选切点；切点之前的消息送去摘要，切点之后的消息**逐字保留**，放在摘要块后面一起发送。切点要落在完整 turn 边界，不能留下未完成的 tool call。保留的 turn 越长，压缩释放的空间越少。
- **可借用**：这是最直接可抄的结构——**旧段摘要 + 最近 N 轮原话**。它同时解决“最近语气/指代/未完成话题不能丢”和“旧段太长”两个问题。
- **不采用/限制**：文档没有给出 N 的选择依据；保留太多会挤压预算；它仍假设摘要本身可信。
- **我们的判据**：最近尾保留 8–12 轮或总预算的 25–35%；尾部的指代消解准确率、语气一致性用人工/LLM judge 对比全量上下文，下降 ≤2 分。

### 2.3 OpenAI：server-side / standalone compaction

- **来源**：OpenAI API Docs, *Compaction*, 2026 — https://developers.openai.com/api/docs/guides/compaction
- **证据级别**：C
- **机制**：`context_management` 里设 `compact_threshold`，跨过阈值后服务端做 compaction，返回一个加密、不可解释的 compaction item；后续请求重放该 item。Standalone `/responses/compact` 是无状态版本，输入完整窗口，返回“新的规范上下文窗口”。文档明确说：**compacted window 通常不只包含 compaction item，还可能包含上一窗口保留的 items**；不要手动裁剪 `/responses/compact` 的输出。
- **可借用**：两点。第一，“压缩结果 + 保留条目”是官方承认的正常形态，不是偷懒。第二，压缩是“生成一个新窗口”，不是“把旧窗口截断”。
- **不采用/限制**：opaque item 不可读、不可审计、不可迁移；对需要人格连续性和事实追溯的 QQ bot，不能把身份/偏好/承诺只存在里面。
- **我们的判据**：opaque 压缩只能用于工具输出/临时任务上下文；人格事实必须落在可读账本里，且能从 `msg_id` 回查。

### 2.4 OpenAI：Codex agent loop 的早期 `/compact`

- **来源**：OpenAI, *Unrolling the Codex agent loop*, 2026 — https://openai.com/index/unrolling-the-codex-agent-loop/
- **证据级别**：C（作者自述）
- **机制**：早期 `/compact` 是用户手动触发，把现有对话加上自定义摘要指令发给 Responses API，得到的 assistant summary 作为后续 `input`。后来才转向原生 compaction。
- **可借用**：手动/半自动触发在早期是合理的；可以先做“关闭段自动摘要 + 全局手动 compact”的混合。
- **不采用/限制**：整段替换，摘要成为唯一输入；没有事实保留率指标。
- **我们的判据**：先灰度“只摘要已关闭段”，观察 2 周事实探针和用户反馈，再考虑是否允许全局 compact。

### 2.5 Anthropic：effective context engineering

- **来源**：Anthropic, *Effective context engineering for AI agents*, 2025 — https://www.anthropic.com/research/effective-context-engineering-for-ai-agents
- **证据级别**：C
- **机制**：把 compaction 定义为“把接近窗口上限的对话摘要后重新开始”，保留架构决策、未解决 bug、实现细节，丢弃冗余工具输出；Claude Code 还会保留最近访问的 5 个文件。文章明确警告：过度激进的压缩会丢掉“后来才显得重要”的细节。
- **可借用**：“保留最近访问的 5 个文件”可以类比成“保留最近 5 个活跃话题/实体”；以及“压缩 prompt 要在复杂 trace 上调”，不能一套 prompt 打天下。
- **不采用/限制**：面向 coding agent，不是聊天；没有量化保留率。
- **我们的判据**：为聊天定义“最近活跃实体/话题”槽位，压缩后这些槽位必须仍可回答；用 50 条“后来才被提到”的延迟问题测。

## 3. 论文机制逐条

### 3.1 MemGPT：分层内存 + 递归摘要 + 完整日志回查

- **来源**：Packer et al., *MemGPT: Towards LLMs as Operating Systems*, arXiv 2310.08560, 2023/2024 — https://arxiv.org/abs/2310.08560
- **证据级别**：A-（预印本 + 公开代码/Letta，实验可复现）
- **机制**：主上下文分三块：system instructions、working context（可编辑事实/persona）、FIFO 消息队列。外部两层：recall storage 存**完整消息历史**，archival storage 存任意长文本/向量库。队列到约 70% 窗口时插入“memory pressure”警告，让模型自己把重要信息写进 working context 或 archival；到 flush 阈值时，队列头部被驱逐，**驱逐消息的递归摘要**放在队列第一个槽位；完整消息仍在 recall storage，可被 `conversation_search` 搜回来。
- **可借用**：这是“摘要 + 原话指针”的完整形态——摘要只负责让模型知道“有这么回事”，真正回答时可以 search 回原话。working context 放稳定人格/用户事实，recall 放全量日志。
- **不采用/限制**：依赖模型自己调用函数，QQ bot 的模型不一定稳定；递归摘要仍可能丢事实，论文没有测“五轮压缩后的规则保留率”；系统复杂度高。
- **我们的判据**：DMR 式深召回：给 bot 只提供压缩上下文，问 100 条跨段事实；允许 `msg_id` 回查后，准确率应从 baseline 提升到 ≥90%（MemGPT 的 GPT-4 32.1%→92.5% 是上限参照，不是我们的目标）。

### 3.2 RecSum / Rsum：递归摘要作为长期记忆

- **来源**：Wang et al., *Recursively Summarizing Enables Long-Term Dialogue Memory in Large Language Models*, arXiv 2308.15022, 2023；Neurocomputing 2025 — https://arxiv.org/abs/2308.15022
- **证据级别**：B（期刊发表；代码“will be released later”，未确认可复现）
- **机制**：两个角色。memory management LLM 先对短上下文生成摘要，之后每次把“旧 memory + 下一段对话”递归生成新 memory；response generator 用最新 memory + 当前上下文回复。没有原话回查层。MSC 上报告后期 session 的 F1/BLEU 提升；但作者明确写了两条限制：预测 memory 与人工金标 memory 的 F1 只有 25.35（Session2）到 29.05（Session4）；以及摘要会出现错误因果关系，**“such incorrect memory might lead to error accumulation”**。
- **同名注意**：2025 年的 ReSum（arXiv 2509.13313）是搜索 agent 的“上下文摘要”方法，不是这篇对话递归摘要；两者不要混用。
- **可借用**：递归更新比每次重摘全量更省 token；memory 要显式包含“人格/偏好”而不只是事件。
- **不采用/限制**：这是最典型的“摘要即记忆”，没有指针、没有事实校验；作者自己承认幻觉会累积。不能作为 QQ bot 的唯一记忆层。
- **我们的判据**：禁止“摘要的摘要”作为唯一输入；每轮递归后 must-keep fact recall 不得低于 95%，且新增事实必须有 `msg_id`。

### 3.3 RAPTOR：递归聚类 + 摘要树 + 跨层检索

- **来源**：Sarthi et al., *RAPTOR: Recursive Abstractive Processing for Tree-Organized Retrieval*, ICLR 2024, arXiv 2401.18059 — https://arxiv.org/abs/2401.18059
- **证据级别**：A（ICLR + 公开代码）
- **机制**：把文本切块、embedding，用 GMM 软聚类（UMAP 降维、BIC 选簇数），对每个簇生成摘要；摘要再聚类、再摘要，直到根节点。检索用“collapsed tree”：把所有层节点放在一起按余弦相似度取 top-k，直到 token 预算（主实验 2000 tokens，约 top-20）。18.5%–57% 的检索节点来自非叶节点，说明高层摘要确实被用上。QuALITY 上配 GPT-4 提升 20 个绝对点。
- **可借用**：段摘要可以组织成树，检索时跨层取；对“这段聊了什么”这类主题问题，高层摘要比单条消息更有用。聚类而不是固定窗口，能避免把跨话题的对话硬切。
- **不采用/限制**：树构建成本高；摘要是检索内容本身，不是指针，仍有摘要幻觉；聊天流是时间序列，纯语义聚类可能把不同时间的同一话题混在一起。
- **我们的判据**：主题型问题（“我们之前聊过的那部电影”）hit@5 ≥90%；摘要节点被引用时，必须能下钻到至少 1 条原话。

### 3.4 Recursively Summarizing Books：递归任务分解 + running summary

- **来源**：Wu et al., *Recursively Summarizing Books with Human Feedback*, arXiv 2109.10862, 2021 — https://arxiv.org/abs/2109.10862
- **证据级别**：B（OpenAI，BookSum SOTA，样本公开；不是对话场景，无可复现代码）
- **机制**：先让人给“小段摘要”做监督，模型学会小段任务后，帮助人给更大的段做反馈；推理时先摘要小段，再递归摘要这些摘要，直到全书。摘要每一层都带“前文 running summary”，避免后段失去前文语境。零样本 QA 用这些摘要能在 NarrativeQA 上拿到 SOTA。
- **可借用**：分层摘要时，子段摘要要携带“前一段的 running summary”，否则后段指代/因果会断；以及“先让小模型做小段，人只审大段”的降本思路。
- **不采用/限制**：书是静态、线性、无交互的；聊天有指代、情绪、话题回跳，不能直接套。书摘要求“覆盖主线”，聊天摘要还要保留“关系状态”。
- **我们的判据**：子段摘要必须包含 `prev_summary_id`；用“跨段指代”问题测，正确率 ≥90%。

### 3.5 SeCom：segment-level 原文检索，明确绕过摘要

- **来源**：Pan et al., *SeCom: On Memory Construction and Retrieval for Personalized Conversational Agents*, ICLR 2025, arXiv 2502.05589 — https://arxiv.org/abs/2502.05589
- **证据级别**：A（ICLR + 公开代码 microsoft/SeCom）
- **机制**：先训练一个对话分割模型，把长期对话切成**主题连贯的 segment**；memory bank 以 segment 为单位，不用 turn（太碎）也不用 session（太粗）。检索前用 LLMLingua-2 对 memory unit 做压缩去噪，但**生成时直接拼接检索到的 segment 原文，绕过 summarization，以避免摘要的信息损失**。在 LoCoMo、Long-MT-Bench+ 上优于 turn/session/summary 基线；分割模型在 DialSeg711、TIAGE、SuperDialSeg 上也更好。二手汇总表里 SeCom 的 LoCoMo LLM-judge 约 56.7（gpt-4.1），仅作参照。
- **可借用**：这是“摘要只做导航/索引，内容用原文”的最干净证据。QQ bot 可以：段摘要做 embedding 索引，命中后返回该段原始消息，而不是返回摘要。
- **不采用/限制**：需要分割模型；segment 太长会超预算；没有解决“段内事实冲突/更新”的问题。
- **我们的判据**：检索命中后，最终 prompt 中 ≥60% 的“事实性内容”来自原文片段，而不是摘要；摘要只占导航 token 的 ≤15%。

### 3.6 MemoRAG：全局记忆生成 clue，再检索原文

- **来源**：Qian et al., *MemoRAG: Boosting Long Context Processing with Global Memory-Enhanced Retrieval Augmentation*, WWW 2025, arXiv 2409.05591 — https://arxiv.org/abs/2409.05591
- **证据级别**：A（WWW + 公开代码）
- **机制**：用一个轻量长程 LLM 把整个数据库压成 global memory（KV 可压缩）；来 query 时，memory 先生成“draft answer / clue”，clue 可能有错、不完整，但能揭示信息需求；然后用 clue 去检索原始 chunk；最后由强 LLM 基于检索到的原文回答。Table 1 平均分：MemoRAG 40.2，Full context 35.0，BGE-M3 RAG 29.7，GraphRAG 29.4。
- **可借用**：这是“摘要只做导航”的量化证据。clue 不需要完全正确，只要能把检索带到正确区域；最终答案必须回到原文。QQ bot 可以用“段摘要 + 事实卡”生成检索线索，再取原话。
- **不采用/限制**：需要训练 memory model；global memory 仍可能漏掉长尾；对短聊天（<20 轮）收益不明显。
- **我们的判据**：clue 检索的 hit@5 相对纯 query embedding 提升 ≥10%；最终回答的引用原话覆盖率 ≥80%。

### 3.7 LongMemEval：压缩成摘要/事实会伤整体 QA

- **来源**：Wu et al., *LongMemEval: Benchmarking Chat Assistants on Long-Term Interactive Memory*, ICLR 2025, arXiv 2410.10813 — https://arxiv.org/abs/2410.10813
- **证据级别**：A（ICLR + 公开代码/数据）
- **机制**：500 条问题，覆盖信息提取、多 session 推理、时间推理、知识更新、拒答；把长期记忆拆成 indexing → retrieval → reading 三阶段。关键发现：长上下文 LLM 在持续交互上有 30%–60% 的性能下降；**把记忆进一步压缩成摘要或单个事实会因信息损失伤害整体 QA，只有多 session 推理这一类例外**；把 key 扩展为“原值 + 抽取出的用户事实”可把 recall@k 提高 9.4%、最终准确率提高 5.4%；时间感知的 query expansion 把时间推理 recall 提高 6.8%–11.3%。
- **可借用**：**“摘要做 value”不如“摘要/事实做 key”**。原文值保留，摘要只用于索引扩展；这正好对应 QQ bot 的“段摘要做索引、原话做 value”。
- **不采用/限制**：benchmark 是英文、合成/半合成对话；知识更新类问题需要显式的 supersede 机制，论文只给了设计方向。
- **我们的判据**：索引 key 用“原话 + 段摘要 + 事实卡”，value 用原话；在 200 条自建 QA 上，整体准确率相对“summary-only”提升 ≥8 个绝对点。

### 3.8 LoCoMo：超长期对话里，长上下文和 RAG 都还不够

- **来源**：Maharana et al., *Evaluating Very Long-Term Conversational Memory of LLM Agents*, ACL 2024, arXiv 2402.17753 — https://arxiv.org/abs/2402.17753
- **证据级别**：A（ACL + 公开数据/代码）
- **机制**：每个人物对话平均 600 turn、16K token、最多 32 个 session；任务包括 QA、事件摘要、多模态对话生成。结论：LLM 在长对话的时序/因果理解上明显吃力；长上下文和 RAG 有改善，但仍显著落后人类。
- **可借用**：评测要覆盖“时序/因果/更新”，不能只测单跳事实；QQ bot 的“上次说的那件事后来怎样了”就是时序+因果。
- **不采用/限制**：英文、机器生成+人工编辑，和中文 QQ 聊天分布不同。
- **我们的判据**：自建评测至少分四类：单跳事实、时序、知识更新、多跳；每类 ≥50 条。

### 3.9 Mem0：抽取事实 + ADD/UPDATE/DELETE 合并

- **来源**：Chhikara et al., *Mem0: Building Production-Ready AI Agents with Scalable Long-Term Memory*, arXiv 2504.19413, 2025 — https://arxiv.org/abs/2504.19413
- **证据级别**：A-（预印本 + 公开代码；LoCoMo 上 26% 相对提升、>90% token 节省、p95 延迟降 91%，均为作者自测）
- **机制**：从对话中抽取 salient facts；写入前检索相似记忆，让 LLM 选择 ADD / UPDATE / DELETE / NOOP；图记忆变体再存实体关系。它不是“摘要”，而是“原子事实账本 + 更新语义”。
- **可借用**：这正是解决“摘要冻结旧事实”的办法——新事实来了就 supersede 旧事实，而不是让摘要同时包含互相矛盾的两版。QQ bot 的“用户换了工作/改了偏好/关系变化”必须走 UPDATE。
- **不采用/限制**：抽取阶段会丢细节；更新判断依赖 LLM，可能误删；没有保留原话指针；作者自测数字不等于我们的场景。
- **我们的判据**：知识更新类问题准确率 ≥90%；每次 UPDATE 保留 `old_fact_id` 和 `source_msg_id`，可审计。

### 3.10 QMSum：query-focused summarization 要先选相关 span

- **来源**：Zhong et al., *QMSum: A New Benchmark for Query-based Multi-domain Meeting Summarization*, NAACL 2021, arXiv 2104.05938 — https://arxiv.org/abs/2104.05938
- **证据级别**：A（NAACL + 公开数据/代码）
- **机制**：给定长会议记录和 query，模型必须**先选出与 query 相关的 span，再对 span 做摘要**；数据含 1,808 个 query-summary 对、232 场会议。它不是“整场会议摘要”，而是“按问题取相关片段再摘要”。
- **可借用**：QQ bot 的压缩也应该是 query-conditioned：当前用户这句话决定取哪段旧聊天，而不是每轮把所有旧段都摘要一遍。
- **不采用/限制**：会议有明确议程，聊天没有；query 可能是“在吗”这种无信息量的。
- **我们的判据**：对无信息量 query，走“最近尾 + 活跃话题”默认上下文，不触发全库检索；对有信息量 query，span 选择 hit@5 ≥90%。

### 3.11 Exploring Neural Models for QFS：两阶段 extractive-abstractive 是强基线

- **来源**：Vig et al., *Exploring Neural Models for Query-Focused Summarization*, Findings of NAACL 2022 — https://aclanthology.org/2022.findings-naacl.109/
- **证据级别**：A（Findings + 公开代码）
- **机制**：系统比较两类方法：两阶段“先抽取 query 相关 span，再 abstractive 摘要” vs 端到端模型；论文的两个建模扩展在 QMSum 上比基线高最多 3.38 ROUGE-1、3.72 ROUGE-2、3.28 ROUGE-L（配合迁移学习）；人工评估显示最好模型的摘要更全面、事实更一致。
- **可借用**：**先抽原话，再摘要**比“直接让模型写一段摘要”更稳；抽取阶段保留了可追溯的 span，摘要阶段只负责组织语言。
- **不采用/限制**：需要标注/训练；聊天没有 query-summary 训练集。
- **我们的判据**：摘要生成前必须先有 `selected_msg_ids`；摘要中每个事实句至少对应一个 span。

### 3.12 HippoRAG：用图索引替代“摘要即记忆”

- **来源**：Gutiérrez et al., *HippoRAG: Neurobiologically Inspired Long-Term Memory for Large Language Models*, NeurIPS 2024, arXiv 2405.14831 — https://arxiv.org/abs/2405.14831
- **证据级别**：A（NeurIPS + 公开代码）
- **机制**：离线用 LLM 做 OpenIE，构建无 schema 知识图谱；在线用 Personalized PageRank 在图上做单步多跳检索，把相关 passage 一次性取回。多跳 QA 比 SOTA 高最多 20%，比迭代检索 IRCoT 便宜 10–20 倍、快 6–13 倍。
- **可借用**：如果聊天里实体/关系密集（人物、地点、事件），图索引比“段摘要向量”更能处理多跳；摘要可以只作为图节点的描述，原话作为节点证据。
- **不采用/限制**：建图成本高；闲聊的实体稀疏，收益可能不如 segment 检索；图谱更新复杂。
- **我们的判据**：多跳问题（“A 上次提到的那个朋友后来怎么了”）准确率相对纯向量检索提升 ≥10%；否则不上图。

### 3.13 对话摘要的忠实性：>35% 不一致

- **来源**：Wang et al., *Analyzing and Evaluating Faithfulness in Dialogue Summarization*, EMNLP 2022 — https://aclanthology.org/2022.emnlp-main.325/
- **证据级别**：A（EMNLP + 人工标注/工具包）
- **机制**：对对话摘要做细粒度人工分析，发现 **超过 35% 的生成摘要与源对话事实不一致**；提出用规则变换生成多选题来评测模型级忠实性，和人工判断强相关。
- **可借用**：对话摘要的失败率远高于新闻摘要；不能因为“摘要有几个关键词对了”就认为没丢事实。评测要用“事实级”判断，不是 ROUGE。
- **不采用/限制**：2022 年的模型，今天的 LLM 可能更好；但失败模式仍然适用。
- **我们的判据**：摘要事实不一致率 ≤2%（按句/事实计），且每个不一致都要能定位到源句。

### 3.14 TOFUEVAL：主题聚焦对话摘要的错误结构

- **来源**：Tang et al., *TOFUEVAL: Evaluating Hallucinations of LLMs on Topic-Focused Dialogue Summarization*, NAACL 2024 — https://aclanthology.org/2024.naacl-long.251/
- **证据级别**：A（NAACL + 专家标注 + 公开数据）
- **机制**：1,479 条主题聚焦摘要、3,966 句，专家逐句标注事实一致性。Summary-level 不一致率：MediaSum 主话题 37.2%、边缘话题 46.0%；MeetingBank 主话题 30.4%、边缘话题 43.6%；GPT-3.5-Turbo 在 MediaSum 上也有 22.2%/27.2%。错误类型中 **Extrinsic Information 占 48.5%**（模型加入对话里没有的信息），其次是语义偏移 15.2%、推理错误 14.1%、指代错误 12.1%。
- **可借用**：摘要 prompt 要显式禁止“补全”和“推断因果”；边缘话题更容易胡编，QQ bot 的闲聊/情绪话题恰恰多是边缘话题。
- **不采用/限制**：会议/访谈对话，不是亲密关系聊天；但错误类型可直接复用。
- **我们的判据**：摘要中“无源句支持”的句子比例 ≤2%；Extrinsic 类错误单独统计，目标 0。

### 3.15 Maynez：intrinsic vs extrinsic hallucination

- **来源**：Maynez et al., *On Faithfulness and Factuality in Abstractive Summarization*, ACL 2020, arXiv 2005.00661 — https://arxiv.org/abs/2005.00661
- **证据级别**：A（ACL + 2,500 条人工标注）
- **机制**：把摘要幻觉分成 intrinsic（歪曲源文）和 extrinsic（加入源文没有的信息）；抽象摘要模型两类都会犯；用 NLI/QA/OpenIE 等指标可以部分检测。
- **可借用**：评测要分开统计“歪曲”和“编造”。QQ bot 的“把用户说的 A 记成 B”是 intrinsic，“用户没说过但摘要加了细节”是 extrinsic，两者修法不同。
- **不采用/限制**：新闻/文章摘要，不是对话；指标在对话上相关性会降。
- **我们的判据**：intrinsic 错误 ≤1/100 事实，extrinsic 错误 ≤1/100 事实；两类分别报表。

### 3.16 Compaction Cliff：类型无关压缩的保留率悬崖

- **来源**：Zerhoudi et al., *The Compaction Cliff in Long-Running AI Agent Memory*, CIKM 2026, arXiv 2608.22752 — https://arxiv.org/abs/2608.22752
- **证据级别**：A-（CIKM + 公开代码/语料；20 个生产 agent 配置）
- **机制**：安全规则和普通 episodic log 争同一份 token，统一压缩时按同样比例被摘要；但规则需要精确措辞才可执行。实测 Claude Code 的 `/compact` prompt 在 Sonnet 4.6 上：一轮后保留 53% 安全规则，五轮后 10%。Knowledge Triage 按类型分五类，三个确定性算子：TypeCompact（按类型保真度原地重写）、TypeDecompose（拆分大主题并复制跨主题规则）、TypeRetrieve（外部存储 + 规则优先召回）。结果：TypeCompact 在五轮后仍有 96% recall，2–4 倍于最强单次 LLM 压缩器；TypeRetrieve recall@50 100% vs 最佳单次检索 73%。
- **可借用**：**按类型分配保真度**。QQ bot 至少分四类：身份/关系事实（不可改写）、偏好/边界（逐条保留）、承诺/待办（逐字保留）、普通闲聊（可激进摘要）。不要用一个摘要 prompt 处理所有内容。
- **不采用/限制**：agent 安全规则不是聊天；但“规则/身份事实需要精确措辞”的机制完全可迁移。
- **我们的判据**：身份/关系/承诺/边界类事实五轮压缩后 recall ≥98%；普通闲聊事实 ≥85%；总体 must-keep ≥95%。

### 3.17 CompactionBench：生产 trace 里的压缩成本

- **来源**：Liu et al., *Benchmarking Long-Horizon Agent Context Compaction with CompactionBench*, Microsoft Research preprint, 2026 — https://www.microsoft.com/en-us/research/wp-content/uploads/2026/10/CompactionBench_preprint.pdf
- **证据级别**：B（正式预印本 + 13.5M 生产 session trace；benchmark 未确认公开）
- **机制**：分析 GitHub Copilot 13.5M 个 agentic coding session、760M 次 LLM 调用：只有 7.8% 的 session 触发 compaction，但它们消耗 44.2% 的总 token；一次 compaction 把 prompt 缩减 72.9%，但 prefix-cache 命中率下降 57.8%。APEC 把“已完成的 trajectory 段”在后台增量摘要，追加到 append-only compacted prefix，活跃 tail 保留；输入 token 降 33.5%、总成本降 25.3%、端到端时间降 9.6%。
- **可借用**：**增量 + 异步 + append-only**。不要每轮重写整本摘要；关闭一段就摘要一段，后台做，活跃段不动。这样既不打断 prefix cache，也不会出现“摘要的摘要”。
- **不采用/限制**：coding agent 的段边界是 tool/trajectory，聊天没有这么清晰；但“关闭段才摘要”的原则可迁移。
- **我们的判据**：压缩后 prompt token 降 ≥60%；prefix cache 命中率下降 ≤10%；摘要任务 p95 延迟不进入主回复路径（后台异步）。

### 3.18 Long Dialog Summarization: An Analysis：没有万能摘要器

- **来源**：Mullick et al., *Long Dialog Summarization: An Analysis*, arXiv 2402.16986, 2024 — https://arxiv.org/abs/2402.16986
- **证据级别**：B（分析型论文，无统一代码）
- **机制**：跨多个领域比较长对话摘要，结论是**没有一个模型在所有领域都好**；购物客服、呼叫中心、开放闲聊需要的摘要维度不同（偏好、问题属性、解决方案 vs 闲聊主线）。
- **可借用**：QQ bot 的摘要 prompt 要按场景分：陪伴闲聊、任务协作、情绪支持，保留字段不同；不要追求一个“通用摘要”。
- **不采用/限制**：分析为主，没有给出可落地架构。
- **我们的判据**：至少两套摘要模板（闲聊/任务），各自的事实召回和人工可读性分开评估。

### 3.19 LongLLMLingua：query-aware token 压缩，作为对照

- **来源**：Jiang et al., *LongLLMLingua: Accelerating and Enhancing LLMs in Long Context Scenarios via Prompt Compression*, ACL 2024, arXiv 2310.06839 — https://arxiv.org/abs/2310.06839
- **证据级别**：A（ACL + 公开代码）
- **机制**：用问题感知的粗到细压缩，删除不相关 token；在 NaturalQuestions 上约 4 倍压缩还能提升最多 21.4%（GPT-3.5-Turbo），并缓解 lost-in-the-middle。
- **可借用**：可作为“索引/检索前的去噪”，类似 SeCom 用 LLMLingua-2 压缩 memory unit 再检索；不适合作为最终上下文，因为它会破坏句子结构和精确措辞。
- **不采用/限制**：token 级删除不是摘要，可能删掉人名/否定词/日期；对人格事实风险高。
- **我们的判据**：只用于检索索引/embedding 前的去噪，不用于最终 prompt；压缩后 must-keep 实体保留率 100%。

### 3.20 Generative Agents：reflection 带指针

- **来源**：Park et al., *Generative Agents: Interactive Simulacra of Human Behavior*, arXiv 2304.03442, 2023 — https://arxiv.org/abs/2304.03442
- **证据级别**：A-（预印本 + 公开代码；UIST 2023）
- **机制**：memory stream 存完整观察；重要性分数累计超过阈值（150）时触发 reflection：取最近 100 条记录，生成 3 个高层问题，用这些问题检索相关记忆，再生成 reflection；**reflection 存回 memory stream 时附带被引用 memory object 的指针**。检索分数 = recency × importance × relevance。
- **可借用**：这是“摘要 + 指针”的另一个证据：摘要不是替代原记录，而是原记录的索引层；每条 reflection 能下钻到被引用的观察。
- **不采用/限制**：importance 由 LLM 打分，主观；没有事实校验；reflection 仍可能错。
- **我们的判据**：每条段摘要/事实卡必须有 `source_msg_ids`；无指针的摘要句直接丢弃。

## 4. 三个关键问题

### 4.1 摘要会不会造成事实漂移/幻觉固化？

**会，而且这不是“模型不够强”的问题，是结构问题。** 证据链：

- 对话摘要本身：EMNLP 2022 测到 >35% 的生成摘要与源对话不一致；TOFUEVAL 在 MediaSum 上的 summary-level 不一致率是 37.2%（主话题）/46.0%（边缘话题），48.5% 的错误是加入对话里没有的信息。
- 多轮压缩：Compaction Cliff 测到安全规则保留率 53%（1 轮）→10%（5 轮）；这不是“摘要质量差”，而是每轮都在丢一点，且丢的是“当时看起来不重要”的精确措辞。
- 递归摘要：RecSum 作者自己观察到错误因果关系，并明确说 “such incorrect memory might lead to error accumulation”。
- 只给摘要的基线：MemGPT 的 DMR 任务里，基线只看到“五轮会话的损失性摘要”，GPT-4 准确率 32.1%；允许搜索完整日志后 92.5%。这说明“摘要作为唯一输入”会把深召回打穿。

**固化机制**：第 1 轮摘要把“用户可能不喜欢猫”写成“用户不喜欢猫”；第 2 轮摘要把这句话当事实，继续写成“用户讨厌猫”；第 3 轮已经没有任何原话可以纠正。每轮都只读上一轮摘要，错误就变成了“先验”。如果没有“原文指针 + 事实校验”，这个链条不可逆。

**最危险的五类内容**：

1. 身份/关系：名字、称呼、生日、亲属、恋爱/友谊状态；
2. 偏好/边界：喜欢/讨厌、雷点、禁聊话题、称呼禁忌；
3. 承诺/约定：答应过的事、时间、地点、礼物；
4. 知识更新：换工作、搬家、分手、改口；
5. 否定/条件：“除非……”“不要告诉别人”“只是开玩笑”。

这五类不能走“自由摘要”，必须走**逐条事实卡 + 原话指针 + supersede**。

### 4.2 有没有“摘要 + 原话指针”的混合方案？

有，而且不止一种。把它们的结构拆开看：

| 形态 | 代表 | 摘要的角色 | 原话/指针的角色 | 证据 |
|---|---|---|---|---|
| **keep-tail** | Anthropic keep-tail | 只摘要切点之前的旧段 | 切点之后最近 N 轮逐字保留 | 官方文档；无量化 |
| **retained items** | OpenAI compaction | 加密 compaction item 携带状态 | 压缩窗口里保留上一窗口的 items | 官方文档；无量化 |
| **摘要 + recall store** | MemGPT | 队列头放驱逐消息的递归摘要 | 完整消息在 recall storage，可 search 回来 | DMR 32.1→92.5 |
| **reflection + pointers** | Generative Agents | 高层 reflection 存回 memory stream | reflection 附带被引用 memory object 指针 | 消融显示 reflection 关键 |
| **segment 原文，不摘要** | SeCom | 段摘要/压缩只用于检索去噪 | 生成时直接拼 segment 原文 | LoCoMo 优于 turn/session/summary |
| **clue → 原文** | MemoRAG | global memory 生成 clue | clue 只用于检索，答案基于原文 chunk | 40.2 vs 35.0/29.7 |
| **原子事实账本** | Mem0 | 不写长摘要，抽原子事实 | 每条事实有来源；更新用 ADD/UPDATE/DELETE | LoCoMo +26% 相对 |

**结论**：最稳的混合不是“摘要里嵌几条引用”，而是**三层分离**：

1. **事实层**：原子事实卡，必带 `msg_id`，可 supersede；
2. **导航层**：段摘要/主题摘要，只用于召回，不作为事实来源；
3. **证据层**：原始消息，命中后整段或窗口取回。

### 4.3 “按 query 检索原话，摘要只做导航”的量化收益

| 方法 | 导航/索引 | 返回内容 | 量化结果 | 证据级别 |
|---|---|---|---|---|
| MemoRAG | global memory 生成 clue | 原始 chunk | 平均 40.2 vs Full 35.0 vs BGE-M3 RAG 29.7（+5.2 / +10.5 绝对点） | A |
| MemGPT | 递归摘要 + recall search | 完整消息 | DMR GPT-4 32.1%→92.5%，ROUGE-L 0.296→0.814 | A- |
| SeCom | segment-level 索引 | segment 原文 | LoCoMo/Long-MT-Bench+ 优于 turn/session/summary 基线；二手汇总 LoCoMo LLM-judge ≈56.7 | A |
| LongMemEval | fact-augmented key | 原值 + 事实 key | recall@k +9.4%，最终准确率 +5.4%；但把 value 压成摘要/事实会伤整体 QA | A |
| RAPTOR | 摘要树跨层检索 | 摘要节点（可下钻） | QuALITY +20 绝对点；18.5–57% 检索节点来自非叶 | A |
| HippoRAG | 知识图谱 + PPR | passage | 多跳 QA 最高 +20%，比 IRCoT 便宜 10–20×、快 6–13× | A |

**关键细节**：LongMemEval 的结论不是“摘要没用”，而是“**摘要/事实适合做 key，不适合替代 value**”。这正好支持“摘要做导航、原话做内容”的设计。

## 5. 对 QQ bot 插件的落地建议

以下只是方案建议，不涉及代码改动。

### 5.1 推荐数据分层

| 层 | 内容 | 生命周期 | 是否可被摘要替代 |
|---|---|---|---|
| `raw_message` | 原始消息，含 `msg_id/chat_id/speaker/ts/reply_to/text` | 永久 | 否 |
| `segment` | 话题连贯的聊天段，含起止 `msg_id`、参与者、时间 | 永久 | 否 |
| `segment_summary` | 关闭段的摘要 + 事实列表 + 未完成话题 + 语气 | append-only | 否，只是导航 |
| `fact_ledger` | 原子事实：主体/谓词/客体/时间/类型/来源/状态 | 永久，supersede | 否 |
| `index` | 段摘要 + 事实卡 + 原话的 embedding/BM25 | 可重建 | 是 |

### 5.2 触发与切段

- **切段信号**：话题漂移（相邻窗口 embedding 相似度下降）、时间间隔（如 >2 小时）、显式结束语（“睡了”“先这样”）、消息数/token 上限、用户明确换话题。
- **关闭段才摘要**：活跃段永不摘要；只有“连续 N 轮没有回到该话题”或“时间间隔足够”才关闭。
- **触发压缩**：上下文达到模型窗口的 60–70%（CompactionBench 生产 median 66%）时，折叠最老的已关闭段；不要等 90%。
- **异步**：摘要任务后台跑，不阻塞主回复；摘要失败就保留原段，不要用空摘要替换。

### 5.3 摘要怎么写

建议摘要不是一段散文，而是结构化卡片：

```text
segment_id: ...
msg_id_range: [1001, 1042]
time_range: ...
participants: ...
topic: ...

facts:
- [identity] 用户叫小林；来源 msg 1003
- [preference] 用户不喜欢被叫“宝贝”；来源 msg 1017
- [promise]  bot 答应周六提醒她考试；来源 msg 1031

events:
- 用户提到下周要搬家；来源 msg 1022
- 两人聊到之前看过的那部电影；来源 msg 1038

open_loops:
- 用户还没决定要不要换工作；来源 msg 1027

tone:
- 整体轻松，末段有点低落；依据 msg 1040-1042

uncertain:
- 用户说“算了”可能指工作，也可能指搬家；不要当事实
```

规则：

- 每条 fact 必须带 `msg_id`；没有来源的不写；
- 不写因果推断，除非原话明确说了“因为/所以”；
- 否定、条件、限定词原样保留（“不是很喜欢”不能写成“不喜欢”）；
- 情绪只写“有原话依据”的部分，不写“她一定很难过”；
- 摘要句如果无法指向具体 `msg_id`，标记 `uncertain` 或删除。

### 5.4 验证流程

1. **Canary facts**：人工标 100–300 条 must-keep 事实，覆盖身份、偏好、承诺、日期、关系、边界、知识更新。
2. **压缩后探针**：只给 bot 压缩后的上下文（摘要 + 保留尾 + 检索片段），逐条问 canary facts；用 exact match / LLM judge 打分。
3. **指针校验**：每条 fact 的 `msg_id` 必须存在且原文支持该事实；用 NLI/LLM judge 检查“摘要句 vs 源句”。
4. **多轮稳定性**：连续 5 轮压缩，画保留率曲线；不能只看第 1 轮。
5. **端到端 QA**：200 条问题，分单跳/时序/更新/多跳/拒答；对比 full-context 和 compacted 的准确率。
6. **成本/延迟**：prompt token p50/p95、压缩比、每轮成本、主回复 p95 延迟。

### 5.5 不采用清单

- **整段历史摘要替换**（Anthropic 默认 / Codex `/compact`）：丢精确措辞、递归漂移、破坏 cache。
- **摘要即记忆**（RecSum 式）：作者自己承认幻觉累积，且没有回查层。
- **opaque provider compaction 存人格事实**：不可读、不可审计、不可迁移。
- **纯 turn-level 向量检索**：太碎，指代/跨轮意图会丢；SeCom 已证明 turn-level 次优。
- **纯 session-level 检索**：太粗，噪声大；SeCom 同样证明次优。
- **token 级压缩作为最终上下文**（LLMLingua 式）：会删否定词/人名/日期；只能做索引去噪。
- **只做摘要、不做事实账本**：知识更新会冻结旧事实；LongMemEval 的 knowledge-update 类会直接暴露。

## 6. 可量化判据

下面是建议的验收表。目标值是“我们场景的目标”，不是论文承诺；论文数字只作为合理性参照。

| 指标 | 定义 | 建议目标 | 测量方法 |
|---|---|---|---|
| 压缩后入字下降 | `1 - compacted_prompt_tokens / full_prompt_tokens`，p95 | ≥60% | 日志统计 |
| must-keep 事实召回（1 轮） | canary facts 中答对/总数 | ≥98% | 压缩后探针 |
| must-keep 事实召回（5 轮） | 连续 5 次压缩后仍答对 | ≥95% | 多轮探针 |
| 身份/关系/承诺/边界召回 | 四类高危事实单独统计 | ≥98% | 人工标注 + judge |
| 事实漂移率 | 每 100 条事实中，与源话矛盾/无源支持的条数 | ≤1 | NLI/LLM judge + 人工抽检 |
| 指针覆盖率 | 带有效 `msg_id` 的 fact/摘要句比例 | facts 100%，摘要句 ≥90% | 结构校验 |
| 检索 hit@5 | canary 问题中，正确原话在 top-5 段/片段 | ≥90% | 检索评测 |
| 端到端 QA 准确率 | 单跳/时序/更新/多跳/拒答 各 ≥50 条 | 相对 full-context 下降 ≤2 绝对点 | LLM judge + 人工 |
| 时序/更新准确率 | 时间推理、知识更新子集 | ≥90% | 自建 QA |
| 主回复 p95 延迟 | 压缩不进入主路径 | 增加 ≤300ms | APM |
| prefix cache 命中率 | 压缩前后对比 | 下降 ≤10% | 上游日志 |

**解释**：

- “入字下降 60%”不是拍脑袋：CompactionBench 生产 compaction 平均缩减 72.9%，我们取更保守的 60%。
- “5 轮 ≥95%”是相对 Compaction Cliff 的 10% 而言；如果做不到 95%，至少要做到“高危事实 98%、普通事实 85%”的分层目标。
- “QA 下降 ≤2 分”是产品可接受线；超过 2 分说明摘要/检索在伤害回答，不是省钱。

## 7. 证据强度与未解决问题

### 7.1 哪些是硬结论

- 对话摘要的事实不一致率很高（EMNLP 2022、TOFUEVAL），不是个别模型问题。
- 多轮压缩会累积丢失，且丢失率可以很高（Compaction Cliff 53%→10%）。
- “摘要 + 原话回查”在多个基准上优于“摘要即记忆”（MemGPT、SeCom、MemoRAG、LongMemEval 的 key/value 分离）。
- 增量、异步、append-only 的压缩在系统成本上明显更优（CompactionBench）。

### 7.2 哪些只是作者自测/生产经验

- Anthropic/OpenAI 的默认阈值、保留策略、prompt 写法：官方文档，没有公开对照实验。
- Mem0 的 26%、91%、90%：作者在 LoCoMo 上的自测，场景和中文 QQ 聊天不同。
- CompactionBench 的 33.5%/25.3%/9.6%：coding agent 生产 trace，不是聊天。
- 社区里的“anchored iterative summarization 98.6% 压缩、质量 3.70 vs 3.44/3.35”：没有可复现实验，只当线索（D）。

### 7.3 还没解决的问题

- **中文闲聊的摘要评测集**：现有论文以英文会议/新闻/合成对话为主；需要自建中文 QQ 风格 canary facts。
- **情绪/关系状态的压缩**：论文几乎不涉及“她今天有点低落”这种状态；这类信息更像“短期状态”，不应该被长期摘要固化，应该有过期时间。
- **多人群聊**：SeCom/LoCoMo 多是双人对话；QQ 群聊的说话人归属、旁听、@关系更复杂。
- **摘要的“可读性”与“事实性”冲突**：结构化卡片事实性强，但可读性差；需要在 prompt 里把卡片转成自然语言时再做一次“不改事实”的约束。
- **成本**：每段一次摘要 + 每次检索一次 embedding，长期看比整段摘要贵；需要按段长度/重要性做预算。

## 9. 一句话给实现同学

**把“摘要”降级为索引，把“原话”升级为证据，把“事实”独立成账本；每次只摘要已经关闭的段，永远不重写整本摘要。**
